## 这 20 份文档里，最该先看的两份

**如果只读两份：**

1. **[第216轮](第216轮-劝阻文案没清干净.md) §六** —— 教你怎么查「模型真正看到了什么」。
   我在这轮之前一直是错的：在源文件里 grep 到「已清干净」就下结论，
   实际那三处文案在 config 和插件描述里，每轮都在进 prompt。
   **正确做法是去 `logs/maisaka_prompt/planner/` 的真实快照里搜。**

2. **[第220轮](第220轮-贴表情当成回应.md) §六** —— 教你怎么看模型的完整行为链。
   「它没反应」不等于「它没试」：它搜了、想回、试了两次、被拦了两次、
   换了个动作、然后以为完成了。**只看最后一轮会完全误判。**

## 通用教训（跨文档）

| 教训 | 出处 |
| --- | --- |
| 「修了」≠「修对了」——改的位置可能只覆盖一半路径 | 第187、192轮 |
| 主动构造场景比等自然发生可靠 | 第187轮 |
| 同一条逻辑只留一个位置，留两处迟早改漏一处 | 第187轮 |
| 先量数据再动手（三层预算实现完才发现不需要） | 第205轮 |
| 门控/拦截逻辑每个分支都要留痕，否则「0 命中」分不清是没调用还是没命中 | 第205轮 |
| 出评测题前必须查库确认期望值唯一性 | 第190轮 |
| 判据看错对象，规则再准也没用 | 第209轮 |
| 「延迟异常大」先问：这个数是几个因子乘出来的，哪个可能无界？ | 第217轮 |
| 放宽门控和变话痨之间只隔一个词 | 第218轮 |
| 不要让旧断言把新行为判成 bug —— 设计变了就同步改断言并注明原因 | 第220轮 |
