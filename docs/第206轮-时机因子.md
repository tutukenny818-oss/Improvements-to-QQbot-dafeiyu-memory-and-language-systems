# 第 206 轮：时机因子（Timing Factor）

> 目标第③项：**用时机因子替代固定间隔**
> 依据 [dsh-speak-up](https://github.com/Yuuyuko-uu/dsh-speak-up)（Tutu 给的）+ 我们的场景改造

---

## 一、原来的问题

`guoke-player` 的"主动想起来"用的是：

```python
wait = base * random.uniform(0.6, 2.2)   # base = interval_minutes * 60
```

**纯随机，不看群里有没有人。**

后果：
- 群里正热闹时，它可能刚好在睡（**错过时机**）
- 群里死寂时，它按时醒来发一条（**显得突兀**）

第 164 轮的历史数据也印证了这点：8 次检查间隔是
`90/84/114/152/94/137/140` 分钟 —— 用户说「跟固定任务一样」。

---

## 二、dsh-speak-up 的思路 + 我们的改造

### 它的设计

```
命中线 = 峰谷命中线 × 时机因子 + 没中加成
掷骰子 < 命中线 才开口
```

时机因子：

| 距**自己**上次说话 | 因子 |
| --- | --- |
| < 20 分钟 | × 0.15 |
| > 360 分钟 | × 1.5 |
| 中间 | × 1 |

### ★ 关键：方向必须反过来

| | dsh-speak-up | 我们 |
| --- | --- | --- |
| 基准 | 距**自己**上次说话 | 距**群里**上次有人说话 |
| 刚活动过 | × 0.15（**少说**，防刷屏） | × 0.5（**多说**，参与） |
| 冷了很久 | × 1.5（**多说**，主动找话） | × 1.8（**少说**，别硬找） |
| 目标 | 不打扰单聊 | 当好群友 |

**它服务的是"一对一陪伴"，我们服务的是"群聊氛围"。方向不能照搬。**

## 三、实现

### 3.1 模块 `src/maisaka/utils/timing_factor.py`

```python
compute_wait_seconds(base, seconds_since_last_group_message=gap)
compute_wait_from_activity(base, last_message_at=ts, now=now)   # 便捷包装
```

参数：

| 项 | 值 | 说明 |
| --- | --- | --- |
| `ACTIVE_RECENT` | 10 分钟 | 小于它 = 热 |
| `ACTIVE_STALE` | 120 分钟 | 大于它 = 冷 |
| `FACTOR_HOT` | 0.5 | 热群提前参与 |
| `FACTOR_STALE` | 1.8 | 冷群别硬找话 |
| `JITTER` | 0.85~1.15 | 保留抖动，避免准点闹钟感 |
| 下限 | 300 秒 | 防止热群时几乎立刻触发 |

### 3.2 接进 `guoke-player`

三处排期统一走 `self._compute_wait(base)`：

```
L785  _proactive_loop 主排期
L793  过期计划重排
L830  _persist_next_check（跳过/检查完后的下一轮）
```

**保留兜底**：时机因子模块挂了 → 退回原来的 `base * uniform(0.6, 2.2)`。

## 五、⚠️ 踩的坑：第一版用错字段，全判成冷群

### 现象

第一版实测分布：

```
旧（纯随机）  : 72 ~ 264 分钟，平均 174
新（时机因子）: 184 ~ 248 分钟，平均 217   ← 全部 ≥180，一个热群都没有
```

**全部落在"冷群"区间。**

### 根因

第一版用 `state["last"]` 当"群里最后活动时间"。但那是
**"上一次有人让它玩"的时间**，不是"群里最后一次有人说话"的时间。

凌晨没人玩 → `last` 一直很旧 → **一直判成冷群** → 等待全部拉长到 ×1.8。

**这会导致「主动想起来」变得更少**，正好和预期相反。

### 修法

改成**查数据库的真实消息时间**：

```python
row = con.execute("SELECT MAX(timestamp) FROM mai_messages").fetchone()
```

### 修复后

```
旧（纯随机）  : 72 ~ 264 分钟，平均 163
新（时机因子）: 73 ~ 263 分钟，平均 165   ← 范围覆盖热/正常/冷三档
```

**范围从「184~248」变成「73~263」，三档都覆盖到了。**

### 教训（第 11 次同类）

**「这个字段看起来像我要的」不等于「它就是我要的」。**

`state["last"]` 名字叫 last，语义是「上次玩的时间」，
不是「群里最后活动时间」。**用之前要查它是谁写的。**

## 六、还没验证的

**真实效果要等群里有活动。**

现在的验证都是离线的（模拟活跃度）。
真正要看的是：
- 群里热闹时，它是否真的会更早参与
- 群里冷清时，它是否真的会更少打扰

**日志关键词**：`主动想起来：时机因子`

---

## 七、这一轮的方法论

### 「照搬别人的设计」要看清方向

dsh-speak-up 的时机因子设计很聪明，但**它的目标和我们的不同**：
- 它：一对一陪伴，别打扰
- 我们：群聊氛围，当好群友

**照搬了机制，但因子方向必须反过来。**

如果直接抄 ×0.15（刚说话就少说），我们的群会变得更死。

### 离线验证 + 真实数据的边界

- 逻辑正确性 → 离线可验（8/8）
- 接线正确性 → 静态 + 动态可验（6/6）
- **真实效果 → 只能等真实场景**

第三项不能靠离线验证替代。**诚实标注「还没验证」比假装验证过更负责。**
