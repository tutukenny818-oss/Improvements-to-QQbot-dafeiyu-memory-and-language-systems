## 〇、结论

**它每次都想到了要催，每次都自己否决了。**

所以它每一轮都在「催 = 急躁」这个前提下做判断，结论必然是沉默。

## 一、改法：登记待回应问句 + 定时唤醒

### 1.1 三个字段

`runtime.__init__`：

```python
self._pending_ask_user_id = ""       # 我问的是谁
self._pending_ask_user_nickname = ""
self._pending_ask_message_id = ""
self._pending_ask_at = 0.0           # 什么时候问的
self._ask_followup_task = None
self._ask_followup_times = 0
```

### 1.2 什么时候登记

`reply` 工具发出消息后，若**发出去的是问句**且**目标是某个具体的人**，就登记：

```python
_note_ask_if_question(runtime, reply_text=..., target_message=...)
```

问句识别 `_looks_like_question()` 三条判据：

- 有问号
- 中文疑问词（怎么 / 为什么 / 是不是 / 能不能 / 哪 / 谁 / 多少…）
- 句尾「吗 / 呢 / 不」

> ⚠️ **不含「吧」**。第一版含了，结果「嗯，睡吧」「行吧」全被判成问句 ——
> 那是应答，不是提问。回归测试当场抓出来（10/13）。

### 1.3 什么时候清掉

`register_message()` 里判发送者：

```python
if ask_sender_id and self._is_ask_replied_by(ask_sender_id):
    self.clear_ask_awaiting_reply(f"{nickname} 已经说话了")
```

**只有「我等的那个」说话才清。** 别人说话不清 —— 那说明他还没回。

### 1.4 什么时候唤醒

```python
ASK_FOLLOWUP_SECONDS = 120.0   # 两分钟没人回
ASK_FOLLOWUP_MAX_TIMES = 1     # 只催一次
```

超时后 `_arm_forced_turn_state()` + `_schedule_message_turn()`，
让 Planner **重新想一轮**。催不催、怎么催仍由它决定 —— 这里只负责「提醒它还有话没落地」。

**定 120 秒的理由**：
- 群里正常人看到消息到回复，中位几十秒，两分钟没动静确实算「没看到」
- 比 wait 默认 30 秒长，不会刚问完就追
- 比「忘了这事」早，上下文还在，催得自然

**只催一次的理由**：真人也不会连催三条。催完还没回就该收手。

## 二、@ 谁：机制上不可能 @ 错

用户特别强调「别 @ 成我了」。好消息是**这个能力系统里早就有**，不用新写。

`reply` 的 `attach_at` 参数：

```python
properties["attach_at"] = {
    "type": "array",
    "description": "可选。随本次回复 at 一个或多个目标消息的发送者，填写目标 msg_id。",
}
```

解析链（`context.py:_resolve_at_attachment`）：

```python
target_message = self.runtime.find_source_message_by_id(target_message_id)
user_info = target_message.message_info.user_info
return AtComponent(target_user_id=user_info.user_id, ...)
```

**填 msg_id → 找到那条消息 → @ 那条消息的发送者。**

所以「@ 对人」的操作定义是：**填你想催的那个人说的那条消息的 msg_id**。
填 Tutu 那条就会 @ 到 Tutu —— 这不是 bug，是「按你说的消息找人」。

### 2.1 提示词三语都写清了

`prompts\{zh-CN,en-US,ja-JP}\maisaka_chat.prompt` 新增一节，中文原话：

> ## ⚠️ @ 谁：只 @ 你问的那个人，别 @ 别人
>
> - `reply` 的 `attach_at` 参数填 **msg_id** —— 它会把 @ 加给**那条消息的发送者**
> - 所以：把「你想催的那个人说的那条消息」的 msg_id 填进 `attach_at`，就一定会 @ 到他
>
> ```
> Tutu: 你先别管他，我这边在弄      ← 这是别人
> 过客: 你猜 / 我说是或不是          ← 这是要催的人
> 你（大肥鱼）: 那个日常用品——是能拿手里的吗
> ```
>
> 你要催的是**过客**，就把过客那条的 msg_id 填进 `attach_at`。
> **填 Tutu 那条就会 @ 到 Tutu** —— 那是催错人，比不催更糟。

用**这次事故的真实对话**做例子，而不是抽象规则 —— 第 193 轮的教训：
模型只认具体反例。

## 五、怎么看它有没有真的催

```powershell
$log = (Get-ChildItem D:\MaiBot\logs -Filter 'app_*.jsonl' |
        Sort LastWriteTime -Desc | Select -First 1).FullName

# 1. 有没有登记
Select-String -Path $log -Pattern '已记下待回应的问题'

# 2. 有没有超时唤醒
Select-String -Path $log -Pattern '的话还没人回'

# 3. 催的时候 @ 了谁（看 attach_at 到底填了什么）
#    去 logs\maisaka_prompt\planner\<chat>\<ts>.json 找 reply 的 args.attach_at
```

**第 3 条是重点**：如果 `attach_at` 填了 Tutu 的 msg_id 而实际要催过客，就是 @ 错人，
那就是提示词的例子还不够具体，要再加真实对照。

## 六、还差的验证

| # | 验证什么 | 判据 |
| --- | --- | --- |
| 1 | 120 秒会不会太短/太长 | 真实场景里催得自不自然 |
| 2 | 会不会在对方离线时硬催 | 若对着离线的人也催，说明没考虑「他可能在不在」 |
| 3 | @ 的是不是对的人 | `attach_at` 的 msg_id → 那条消息的发送者 = 提问对象 |
| 4 | 催完还没回会不会继续缠 | 有 `ASK_FOLLOWUP_MAX_TIMES=1` 兜着，日志里不该出现第二次 `的话还没人回` |

**第 4 条是回归红线**：同一个问句出现两次「还没人回」= 计数器坏了。
