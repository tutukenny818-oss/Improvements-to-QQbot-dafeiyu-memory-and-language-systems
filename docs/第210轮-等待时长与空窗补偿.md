# 第 210 轮 · 回复慢在哪：43 秒的构成

> 用户问「大肥鱼回复时间长是因为现在得等全消息嘛」。
> 答案：**不是。七成时间花在「等人凑够数」，不是「等消息发全」。**

---

## 〇、一句话结论

`talk_value = 0.5` → 触发阈值 **2 条消息**。你只发 1 条 → 不够阈值 →
走「空窗补偿」，而补偿速度的下限被钉死在 **30 秒**（`runtime.py:92`）。

**「2 条消息」实际执行起来等于「等 30 秒」。**

差的 33 秒全在第一段。

## 二、那个 2 秒不是原因

`连发消息静默窗口（2.0 秒）` 是另一件事——防止你连发 3 条被逐条回答：

```
02:31:01  连发消息静默窗口结束（2.0 秒），合并接入 2 条
```

它把「喜欢你」+「[表情包]」合并成一轮处理，避免回答两次。
**2 秒，占 5%。** 用户感觉到的"慢"不在它。

---

## 三、空窗补偿的公式

`src/maisaka/turn_trigger/gates.py`：

```python
idle_equivalent_count = min(idle_seconds / average_message_interval, trigger_threshold - 1)
equivalent_message_count = pending_count + idle_equivalent_count
if equivalent_message_count >= trigger_threshold: → 触发
```

`average_message_interval` 有个下限（`runtime.py:92`）：

```python
IDLE_COMPENSATION_MIN_AVERAGE_INTERVAL_SECONDS = 30.0
```

也就是：

```
补满第 2 条所需空窗 = (2 - 1) × 30 = 30 秒
```

**这个下限的本意是防止冷群反复自我唤醒，代价是单条消息必等 30 秒。**

---

## 四、修法：30 → 15

```python
IDLE_COMPENSATION_MIN_AVERAGE_INTERVAL_SECONDS = 15.0
```

### 效果

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 1 条普通消息 | 43.3s | **≈28.3s** |
| 被 @ / 戳一戳 | ≈10s | ≈10s（不受影响） |

### 验证（`tools\_p210_idle_compensation_verify.py`）

```
[PASS] 空窗补偿下限 = 15.0s
[PASS] talk_value=0.5 → 阈值 2 条
[PASS] 空窗 15.1s → 触发进入 Planner
[PASS] 空窗 14.9s → 仍延迟，剩余 ≈0.1s
[PASS] 平均间隔 60s → 不会提前触发
[PASS] pending=0 → 绝不靠纯沉默触发
[PASS] 端到端预估 ≈28s（改前 43s）
```

### 没有动的底线

- `pending_count = 0` 时一律不触发（没人说话不自己开口）
- 空窗折算封顶在 `trigger_threshold - 1`（不能纯靠沉默跨阈值）
- 群本身很慢（平均间隔 60s）时折算同样变慢——这是对的，不该硬找话
