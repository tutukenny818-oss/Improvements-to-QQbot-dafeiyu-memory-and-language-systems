## 二、01:58-a：守卫把「想回」误判成「不想回」

### 证据

第二条 Planner 正文（`1792605268209`）：

> …抓他出尔反尔（「刚才不是说不忙了」），带点幸灾乐祸…**一两句收住**。
> **不需要工具**：只是一个接梗的反应…也不发图（刚上下文里图已经不少了）。

旧守卫的判定过程：

```
末 100 字 EXPLICIT_NO_REPLY 命中: None
末 220 字 NO_REPLY    命中: '不发'   ← 「也不发**图**」的「发」！
末 220 字 REPLY_INTENT 命中: '吐槽就够'
→ NO_REPLY 一票否决 → has_unsent_reply_intent = False
```

第三次（`1792605544068`，Tutu 已经说「不出来伤心了」）更荒唐：

```
末 220 字 NO_REPLY 命中: '等，还是得出来'   ← 「人既然在等，还是得出来」被判成"继续等待"
```

正文写着「**必须回**」「**还是得出来**」，守卫判 False。

### 修法（`planner_reply_guard.py` 重写判定顺序）

| 顺序 | 判据 | 为什么排这个位置 |
| --- | --- | --- |
| 1 | 末段明确「调用 reply」 | 最确定 |
| 2 | **最强发言词**（必须回 / 还是得出来 / 该回一句） | 排在沉默**之前** —— 「不回就是装死，必须回」是否定之否定 |
| 3 | **结论级沉默**（不发言 / 保持沉默 / 不调任何工具） | 只有这种才否决，重试没意义 |
| 4 | 较弱发言表述（回一句就好 / 吐槽就够 / 一两句收住） | |
| 5 | 打算调别的工具（先看 / 查一下 / wait 一会） | |
| 6 | 其余 | 不重试 |

关键改动：`发` 不再单独当「不发言」的证据；`等…出来` 不再否决；强发言词优先于一切沉默词。

### 验证：22 个真实「没调工具」轮次全对

```
命中=8  漏判=0  误判=0  合计=22
```

（标注是我逐条读全文定的：8 条确实该动手，14 条确实该沉默）

## 三、01:58-b：门控把「点名」吃掉了

### 证据

```
01:58:39  Tutu: 大肥鱼！              ← 明确点名
01:58:53  Tutu: 不出来伤心了          ← 补一句
01:58:53  判定=进入Planner
01:59:04  Planner 已结束本轮思考      ← 8.2 秒，什么都没发
```

Planner 正文其实写得很好：

> **这是明晃晃的 I1——点名 + 情绪加码…不回就是装死，必须回。**
> 方向上：先回应「被叫」这件事…**还是得出来**…

但 `reply` 工具从头到尾**没被执行**（`maisaka_builtin_reply` 0 命中），
因为「必须回」那轮被 §二的守卫判成 False 直接结束了 —— 根本没走到门控。

**如果它真的调了 reply，门控会怎么判？**

```python
evaluate(latest_text="不出来伤心了")  → allow=False  S1  别人闲聊，没提到 bot
evaluate(latest_text="大肥鱼！")      → allow=False  S2  第三人称提到 bot
```

门控只看 `message_cache` 里**最后一条**他人消息。「大肥鱼！」「不出来伤心了」两条连发，
点名那半句被"补一句"盖掉，只剩一条没名字没问号的 S1。

`_ADDRESS_MARKERS` 里也没有 `！` —— 「大肥鱼！」连"叫名字+指令"都不算。

**这是第二道会吃掉这条回复的闸。** 只修 §二 的话，这一轮会卡在门控上。

### 修法

1. `activation_gate.evaluate()` 新增 `recent_texts` 参数：
   窗口内只要有一条是 I1（@ / 点名），就放行。
   > 事故现场（01:58）：只看最后一条 → S1 → 拦。点名那半句被"补一句"盖掉了。
2. `_ADDRESS_MARKERS` 补上 `！` `!` `…` —— 「大肥鱼！」本来就是喊人。
3. `reply._check_activation_gate()` 把窗口里更早的他人消息一起传进去（跳过 bot 自己的）。

### 验证

`tools\_p208_gate_window_verify.py` —— 12/12：

```
PASS  ★01:58 事故：窗口带点名      allow=True  I1  窗口内上一条叫名字+指令（大肥鱼 + '！'）
PASS  真闲聊：窗口无点名           allow=False S1
PASS  真闲聊：窗口是别人对话        allow=False S1
PASS  第三人称议论                allow=False S2
```

真实 `SessionMessage` 对象重放：

```
01:58 事故重放     窗口=['大肥鱼！'] -> allow=True  I1
01:48 那条         -> allow=True  I2（平台判定提及 bot）
纯闲聊两连发       窗口=['今天吃了碗面'] -> allow=False S1
中间夹 bot 自己    窗口=['大肥鱼！'] -> allow=True  I1
```

旧门控回归 `_p205_gate_live.py` 仍 5/5（S1 84%、S2 91% 拦截，I1/I2 全放行）。

## 七、排查顺序（「没回应」按这个走）

```powershell
$f = (Get-ChildItem D:\MaiBot\logs -Filter 'app_*.jsonl' | Sort LastWriteTime -Desc | Select -First 1).FullName

# 1. 消息进来了吗
Select-String -Path $f -Pattern '<关键词>' | Select -Last 5

# 2. 进 Planner 了吗
Select-String -Path $f -Pattern '进入Planner|判定=延迟检查' | Select -Last 5

# 3. Planner 输出里有工具吗（最容易被忽略）
#    logs\maisaka_prompt\planner\<chat>\<ts>.json 的 output_items
#    只有 AssistantMessageItem = 想完就结束，一个字都不会发出去

# 4. 守卫认出来了吗
#    同一份 JSON 的正文丢进 has_unsent_reply_intent()

# 5. reply 工具跑了吗
Select-String -Path D:\MaiBot\logs\app_*.jsonl -Pattern 'maisaka_builtin_reply'

# 6. 门控拦了吗
Select-String -Path D:\MaiBot\logs\app_*.jsonl -Pattern '激活门控'

# 7. 适配器策略拦了吗（入站就被丢）
Select-String -Path $f -Pattern '入站被策略拦截|Host 丢弃了'
```

**第 3、4 步是这轮补上的**。1→2→3 正常但没发出，问题只可能在：
守卫没认出来 / 门控误杀 / reply 执行失败 三者之一。
