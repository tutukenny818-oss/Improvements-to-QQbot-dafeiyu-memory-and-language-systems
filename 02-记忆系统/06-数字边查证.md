## 二、数字边：为什么不能删

### 2.1 调查方法（第一版错了）

第一版按 `fact_claims.value_text = "967"` 精确匹配 → **0 条命中**。

原因：`value_text` 存的是**整句**，不是裸数字：

```
过客的壳币数量为138
《老经》的壳币数量为 552
```

改成「在 `value_text` 里搜该数字 + 主语也出现在同句」后，18 条里有 14 条"命中"。

### 2.2 但命中里有多数是假阳性（实测）

| 边 | 匹配到的 fact_claim | 判断 |
| --- | --- | --- |
| `大肥鱼 --壳币数达到--> 912` | 「大肥鱼在24点抢答中…获15壳币」 | ❌ **数字碰巧**，不是同一条 |
| `过客 --壳币余额为--> 547` | 「…获得 +100 壳币…」 | ❌ 同上 |
| `大肥鱼 --在果壳拥有壳币--> 242` | 「…成功猜出「水球」…」 | ❌ 同上 |

**数字相同 ≠ 同一条事实。** 所以「14 条已有对应，可安全删」这个结论是错的。

### 2.3 4 条确实没有对应（实测）

```
大肥鱼 --壳币有--> 877        src=40f071427b2b2616f6
大肥鱼 --壳币数为--> 877      src=0014f0430e20493280
大肥鱼 --壳币数量--> 967      src=48e291b38cfc433f59
大肥鱼 --壳币累计达到--> 967  src=9398b17653c45ca11f
```

删这 4 条 = 大肥鱼「877 和 967 这两个数」在事实层没有任何记录。

### 2.4 还有 7 个段落会变孤证（实测）

18 条边**每一条都被 1 个段落引用**，其中 7 个段落删完只剩 0~1 条关系：

```
0014f0430e20493280…  现有 2 条
009cb167decad194a3…  现有 1 条 ← 会变孤证
28be2085f7381e8a04…  现有 1 条 ← 会变孤证
40f071427b2b2616f6…  现有 1 条 ← 会变孤证
48e291b38cfc433f59…  现有 1 条 ← 会变孤证
```

### 2.5 决定

**只标注，不处理。** 理由三条：
1. 删了会丢 4 条事实 + 7 个段落少证据
2. 「已有对应」不可靠，不能作为删除依据
3. 真正该修的是**时间抽取**（§三），修完这批边的时间戳才可信

**落地方式**：在健康检查里加一项盯着「relations 里 object 是纯数字的比例」，
超过 15% 就报 WARN。这样它不会悄悄变多，也不用删数据。

## 三、`valid_to` 早于 `valid_from`：分清两种

### 3.1 规则本身是对的（论文原文实读）

Tutu 问「是不是特地让 to 早于 from 的」——**是的，这是 Zep 的设计**。

[Zep arXiv:2501.13956 §2.2.3](https://arxiv.org/html/2501.13956v1) 原文：

> "the system tracks four timestamps: `t'created` and `t'expired ∈ T'` monitor when facts
> are created or invalidated in the system, while `t_valid` and `t_invalid ∈ T` track the
> temporal range during which facts held true."
>
> "When the system identifies temporally overlapping contradictions, it invalidates the
> affected edges by setting their `t_invalid` to the `t_valid` of the invalidating edge."
>
> "Following the transactional timeline `T'`, Graphiti **consistently prioritizes new
> information** when determining edge invalidation."

**关键**：`t_invalid` 取自**新边的 `t_valid`（事件时间）**，不是处理时间。
所以只要新边的事件时间在语义上更晚，`旧.t_invalid > 旧.t_valid` 就成立，属正常。

### 3.2 实测：我们的数据分两类

**A 类：正常**（`t_invalid` 落在同一批对话内，代表「这件事在这轮里发生变化」）

```
10-21 10:09 创建  → valid_to = 10-21 10:08   差 1 分钟
  原文：「《老经》的果壳壳币余额最终变为 100。」
  → 同一条摘要里先 532 后 100，失效时刻在窗口内，正常

10-20 14:30 创建  → valid_to = 10-20 14:26   差 4 分钟
  → 同上
```

**B 类：真 bug**（`t_invalid` 落在**创建时间所属段落之前**，物理上不可能）

```
10-19 23:55 创建  → valid_to = 10-18 07:29   倒挂 1 天多
  → 10-19 才写进库的事实，说它 10-18 就失效了？
    只能是相对时间（「昨天」「上次」）按错误的 t_ref 换算出来
```

### 3.3 判据（可写成检查项）

```
真 bug  ⇔  valid_to < min(该 claim 所引用段落的时间窗 t_start)
正常    ⇔  valid_to ∈ [该 claim 所引用段落的时间窗]
不可能  ⇔  valid_to < valid_from（同一行内倒挂）   ← 也要查，本轮未发现
```

### 3.4 根因（已定位，两次判断被推翻）

**★★ 更正 1**：我先说「根因是用消息时间做换算」→ **撤回**。
实测 `fact_claims.valid_from` **空 92/92（100%）**，代码 `metadata_fact.py:561`：

```python
supersede_at = normalized_valid_from if normalized_valid_from is not None else now
```

`valid_from` 全空 → **永远走 `else now`**。没有「相对时间换算」参与。

**★★ 更正 2**：我说「相对时间按错误 t_ref 换算」→ **撤回**。同上，没这回事。

**真正根因**：`fact_transitions` 里 **7 条 transition 的时间早于被淘汰 claim 的创建时间**，
即「更早创建的记录淘汰了更晚创建的记录」，与「后来者优先」（Zep 原文
`t'` 轴上 `consistently prioritizes new information`）相反。

```
transition@10-18 07:29:41  type=supersede
  old claim created@10-19 23:55:05      ← 被淘汰的是 10-19 的
  new claim created@10-18 07:29:41      ← 淘汰它的是 10-18 的
```

### 3.5 但 7 条里只有 1 条真异常

按倒挂时长分档（实测）：

| 倒挂时长 | 条数 | 性质 |
| --- | --- | --- |
| < 1 小时 | 7 | **正常**。同一批对话里有多条摘要，`created_at` 是**入库顺序**，`supersede` 是**语义顺序**。摘要「532 → 552 → 100」在一段对话里说完，两者本来就可能不一致 |
| > 1 天 | **1** | **真异常**。10-19 写的被 10-18 的淘汰，物理上不可能 |

所以真正要修的是**那 1 条**，不是那 7 条也不是全部 26 条 supersede。

### 3.6 外部资料

- 双时间轴动机见 [Zep 论文](https://arxiv.org/html/2501.13956v1) §2.1：
  `T` = 事件时间轴，`T'` = 事务时间轴，**两者不能混用**
- 我们的映射：`valid_from`/`valid_to` ∈ `T`；`created_at`/`expired_at` ∈ `T'`
- 论文 §2.2.3 原文两句都在本节被引用，**规则本身没写错，是我们的数据有 1 条违反它**

### 3.7 已加入健康检查的判据（实测生效）

`_p179_memory_health.py` 新增两项：

```
[v] 关系里的数字边      18/167（11%），已知基线 11%，只监控不删
[!] 失效时间跨天倒挂     1 条（valid_to 比创建时间早 1 天以上）
```

判据：`valid_to < created_at - 86400` 才算 WARN。
**同批对话内失效（<1 小时）不计入**，避免误报那 7 条正常记录。

## 四、壳币 4 个"当前值"（实测，未解决）

### 4.1 四个数字

| 来源 | 值 | 时间 | status |
| --- | --- | --- | --- |
| `fact_claims`（direct_user） | **972** | 10-21 00:52 首次 / 10-21 07:35 最后确认 | active |
| `relations` | **967** | 10-21 21:19 / 21:32 | 未标记失效 |
| `relations` | **877** | 10-21 19:05 / 20:15 | 未标记失效 |
| `fact_claims`（summary_derived） | **767** | 10-20 01:32 | superseded（10-21 12:58） |

### 4.2 为什么问答会错

问「大肥鱼现在有多少壳币」，检索会同时命中 767 / 877 / 967 / 972 四条，
其中 877 和 967 在 `relations` 里**都没被标记失效**，模型看到矛盾就答不准
（这正是第 189 轮 `stale_claims.py` 想解决的那类问题，但那个模块只覆盖人设）。

### 4.3 谁的语义最新（实测推断）

按**事件时间**（不是入库时间）：

```
10-20 01:32  767   ← 最旧
10-21 19:05  877
10-21 21:19  967   ← 最新（relations，今晚 21:19 写入）
```

但 `fact_claims` 里 active 的是 **972**（10-21 00:52 首次观察，07:35 最后确认）。

**972 是 10-21 早上的值，967 是 10-21 晚上的值 —— 967 更晚**，
但 972 的 `last_confirmed_at` 更早，所以按「最后确认」排序会选 972，是错的。

**推测**：`last_confirmed_at` 只在特定写入路径更新，`relations` 那条路径不更新它。
这就是「同一分钟内多个矛盾数值」问题的机制。
