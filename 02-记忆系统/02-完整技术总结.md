## 三、修了什么（按影响排序，全部有事故依据）

### 3.1 ★★★ 每天在丢消息：摘要游标失效

**症状**：某些时段有几十条对话，但一个记忆段落都没产生。

**根因链**（跨三个模块）：
```
图片描述触发的摘要 → 不带 trigger_message_count
  → 重启后恢复逻辑退化成 return total（把游标设成"现在"）
    → 重启前那批还没被摘要的消息被永久跳过
```

实测 10-20 三个时段有消息但零段落：17:00（39 条）、18:00（31 条）、23:00（63 条）。

**修法（三处）**：写段落时补齐游标 + 有内容时也记检查点 + 缺游标时用 `event_time_end` 推算。

### 3.2 ★★★ 身份认知被污染：大肥鱼否认自己的形象

**症状**：它说自己是「蓝发黑西装」，否认女仆装形象。

**查证**：抽取没错 —— 是它被 B 站评论区带偏后说的错话，摘要如实记录，
被检索召回，形成**自我污染闭环**。

**修法（三层）**：
1. 人设层：`bot_config.toml` 加硬规则，**点名那句错话**
2. 事实层：2 条 `authority=manual` 权威认知进画像
3. 检索层：`stale_claims.py` 给旧说法打 `⛔已被推翻,不要采信`

实测：问「你长什么样」→「蓝紫渐变长发，深蓝小裙子配绣鲸鱼的围裙，后面还拖着条鱼尾」（6/6 × 3 次）

### 3.3 ★★★ 一条摘要只记到 25%：偏好/承诺类事实全丢

**症状**：92 个对话摘要只有 23 个产出事实（25%）。

**根因**：`_write_summary_metric_claims` 只处理 `cardinality='single'`，
而 `pref.like`、`pref.habit` 全是 `set` → **一条偏好都没抽过**。

**修法**：拆出两条新路径

| 类型 | 依据 | fact_key 策略 |
| --- | --- | --- |
| 偏好（`_write_qualitative_claim`） | VARS 双轨原则（稳定 vs 瞬时） | 复用 `pref.like`，set 多值共存 |
| 承诺（`_write_commitment_claim`） | MS-TOD `confirmation state` | **带日期 + 内容指纹**（有生命周期） |

### 3.4 ★★ 检索排序：试了但失败，已回滚

**问题**：「答应过什么」排第 9。

**试的方案**：高分 episode 插队。

**结果**：`recall@1` **83% → 58%**（掉 25 个点），换 recall@5 +8 个点。**净负优化，回滚。**

**根因**：段落是余弦（0~1），episode 是词法分（0~24.5），**量纲不同不能混排**。

> **这次失败最有价值** —— 那次改动单测全绿、严评 15/15、健康 0 异常，
> 只有新建的召回指标能看出来。

### 3.5 ★★ 时间上限只对一条路径生效

**症状**：库里 23 条摘要跨度 >2 小时（最长 18.6h），而 `max_window_hours=2.0` 明明配了。

**根因**：`image_description_compensation` 这条写路径**漏传 `window_time_start`**。
**同一位置第 187 轮也漏过**（漏的是游标）—— 一个功能有多条入口是新 bug 的温床。

修复后的决定性证据：

| 分组 | 条数 | 最长 | >2h |
| --- | --- | --- | --- |
| 有 `window_time_start` | 10 | **2.0h** | **0 条** |
| 无（历史） | 91 | 18.6h | 23 条 |

### 3.6 ★★ 2 个插件入口从来没被调用过

**症状**：`bili-scout` 的 `/刷视频`、`video-eye` 的视频预读一次没生效。

**根因**：`bot.py:872` 的 `emit(ON_MESSAGE)` 被注释掉，全仓无别处 emit。

**修法**：补 `chat.receive.after_process` HookHandler（和已验证工作的 human-life 同模式）。

### 3.7 ★★ 噪音：episode 通道有零分命中

**根因**：`_fuse_branches` 算完 RRF 分**就 pop 掉了**，下游读不到 → 恒为 0.0。

**修法**：改名保留 `fusion_score`；加 `HEAD_RANK_LIMIT=5` + 相对分数阈值。
结果：episode 零分命中 4 → **0**。

### 3.8 ★ 事实太长 + 写入噪音

- 157 字的「事实」→ 定量指标按「主语+指标+值」拼短句（157 → 14 字）
- 承诺句 → 取第一个逗号前（61 → 20 字，依据 AtomMem 原子事实）
- prompt 加**六类明确排除清单**（一次性的话/临时状态/一次性行为/太模糊/别人的评价/闲聊），实测 8/8

## 六、第 194~195 轮的新发现（这一阶段刚查清的）

### 6.1 `relations` 会**编造数字**

```
大肥鱼 --壳币数为--> 877
  对应 source_paragraph 原文：「…大肥鱼抢先答对了两次并累计拿到壳币…」
  原文里一个数字都没有
```

这不是「抽错」，是**凭空生成**。比数字边污染严重 —— 数字边只是没用，编造值是**主动误导**。

验证工具：`tools\_p195_final_verdict.py`

### 6.2 两条写路径策略不一致 → 同一指标多值并存

| | `fact_claims`（规则抽） | `relations`（LLM 抽） |
| --- | --- | --- |
| 数值校验 | 有 | **无** |
| 冲突处理 | 「数值下降不取代」 | **无** |

具体：段落「壳币增至877」→ 规则链**正确抽出 877**，但当时 active 是 972，
877 < 972 属「数值下降」→ 保守策略**不写入**；同一次 LLM 调用的 `relations[]`
没有这条规则 → **877 照样写进 relations**。

结果：壳币有 5 个"当前值"并存（767 / 847 / 972 + 877 / 967）。

### 6.3 三件事经查证后判定**不该做**

| 事项 | 原计划 | 实际结论 |
| --- | --- | --- |
| 18 条数字边分流 | 删掉或迁移 | **删了会丢信息**：4 条无对应事实、7 段变孤证、14 条「已有对应」是假阳性 |
| 两道 recall 失分题改内容 | 压缩承诺句、补同义表述 | **短 query 稀释**（加长 query 立刻第 1）+ **跨通道量纲**（10 种校准方法全 ≤ 基线） |
| 关系类事实双向性 | 补反向边 | **166/167 天生单向**，补反向是语义垃圾 |

## 八、这个阶段最重要的一条方法论

**「建指标」比「改代码」更重要。**

18 轮里最关键的转折不是某个 bug 被修好，而是三次建指标：

- 第 184 轮：八维度盘点
- 第 185 轮：噪音量化
- 第 190 轮：召回准确率

**在建指标之前**：改完只能说「感觉好点了」，改坏了也发现不了。
**在建指标之后**：episode 插队那次，单测全绿、严评 15/15、健康 0 异常，
**只有召回指标能看出 recall@1 从 83% 掉到 58%**。

**没有指标就只能靠感觉，靠感觉就会一直修错地方。**

## 九、诚实的自我评估

**做得好的**：底线稳固（30/30、recall@10 100%、证据链 0 缺失），且任何改动都有指标兜底。

**还差的**：数值类事实这条链是漏的 —— 编造、多值并存、下降被误判，三个问题叠在同一处。

**我这几轮错了 5 次**（都记在 `记忆系统演进.md` 和交接文档里）：

1. 说「时间戳因果反转」→ `valid_from` 空 100%，假设不成立
2. 说「相对时间按错误 t_ref 换算」→ 同上
3. 说「生产代码把纯数字传给校验函数」→ 是我诊断脚本自己传错
4. 连续三次出题出错（`正经点` 归属、期望值过时、547 归属）
5. 差点把本地扩展的 `max_window_hours` 报成上游 bug

**教训**：报根因前先统计字段空值率；下结论前先读调用点原文；动手前先 `git grep HEAD` 确认功能在上游存在。
