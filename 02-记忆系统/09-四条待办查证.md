## §1 插件 hook：真实触发**已经被证明**了，只是 log 关键词搜错了

### 原待办写的是

> 插件 hook 真实触发验证 —— 元数据已对齐对照组，缺一条真实消息

### 实际情况

**早就触发了。** 证据在 `D:\MaiBot\logs\app_20261021_210138.log.jsonl`：

```json
{"event": "拟人入口：群=GROUP_ID 人=USER_A_QQ @=0 notice=0 own=False",
 "logger": "human_life", "level": "debug", "lineno": 1067,
 "module": "plugins.human-life.plugin"}
```

这条 `拟人入口` 日志在 `human-life/plugin.py` 的第 1067 行，而它所在的函数
`_handle()` 只被 `on_after_process()` 调用，`on_after_process()` 挂的正是
`@HookHandler("chat.receive.after_process", mode=HookMode.OBSERVE)`（第 998~1005 行）。

**所以 `chat.receive.after_process` 这条 hook 确实在真实消息上跑了**，
`human-life` 走通了，`bili-scout` 和 `video-eye` 挂的是同一套模式。

### 为什么之前判断成"没触发"

搜日志时用了 `after_process` / `bili_scout` / `video_eye` 当关键词，
但**这三个插件都不在 hook 里打自己的名字**：

| 插件 | hook 里打什么 |
| --- | --- |
| `human-life` | `拟人入口：群=… 人=…` ← 有日志 |
| `bili-scout` | 只在**真的匹配到触发词**时才打（`预读视频` / `手动看视频`），平时静默 |
| `video-eye` | 同上，平时静默 |

所以「日志里没有 `bili_scout` 的 hook 记录」= **群里还没人发过「刷视频」**，
不等于 hook 没跑。

### 真正的新问题（这条才值得盯）

`bili-scout` 启动自检拿不到会话：

```json
{"event": "chat.get_group_streams -> 0 个会话（原始类型 list）", "level": "info"}
{"event": "chat.get_group_streams 没解出会话，原始返回：'[]'", "level": "warning"}
{"event": "chat.get_all_streams -> 0 个会话（原始类型 list）", "level": "info"}
{"event": "启动自检：可用群会话=（空）"}
```

查了上游实现 `src/plugin_runtime/capabilities/data.py:250`：

```python
def _list_sessions(self, platform: str, is_group_session=None):
    from src.chat.message_receive.chat_manager import chat_manager
    return [s for s in chat_manager.sessions.values()
            if (platform == "all_platforms" or s.platform == platform)
            and (is_group_session is None or s.is_group_session == is_group_session)]
```

**是内存里的 `chat_manager.sessions`**，插件在 `on_load` 时查，此时还没收到任何消息
→ sessions 为空 → 返回 `[]`。这是**启动时序问题，不是 hook 问题**。

好消息：`_pick_auto_target()` 每次触发都重新调 `_group_streams()`（没有缓存），
所以真发「刷视频」时 `chat_manager` 里已经有会话了，能取到。
**结论：自检那两条 warning 是无害噪音，可以降成 debug。** 只有 `_first_group_stream()` 这种
`on_load` 阶段就直接取会话的旧调用才会有问题（第 758 行，目前没被 hook 走到）。

### 处理

- ✅ 待办 #1 **可以划掉**（hook 已被 human-life 的真实日志证明）
- 📌 新开一个小项：把 `bili-scout` 的自检日志从 `warning` 降级，并在 `on_load` 时跳过会话探测
- 📌 仍然等一条真实「刷视频」来验证端到端（这个等不来就是等不来，不阻塞）

## §2 分数校准：上游早就有，**10 种全试过，没有一种能超过基线**

### 原待办写的是

> episode/段落分数校准 —— 要混排得先校准，需要标注数据

「需要标注数据」这个判断**只对了一半**。查了代码：

### 上游本来就有校准模块

`src/A_memorix/core/retrieval/score_calibration.py`，支持 **13 种方法**：

```python
SCORE_CALIBRATION_METHODS = {
    "none", "minmax", "rank_percentile", "robust_sigmoid",
    "semantic_minmax", "semantic_graph_rrf", "semantic_rank_percentile",
    "semantic_robust_sigmoid", "semantic_rrf", "semantic_sparse_rrf",
    "semantic_softmax", "softmax", "weighted_rrf",
}
```

配置项 `retrieval.vector_pools.score_calibration_method`，默认 `"none"`。
模块 docstring 写得很明白：

> 「该模块只处理已经召回的候选分数，不负责召回、过滤或图证据质量判断。
> 所有方法都保持候选集合不变，便于**在同一批数据上比较标度校准对排序的独立影响**。」

——**这正是第 191 轮想做而没做成的那件事**，上游已经建好了实验框架。

外部资料也支持这个方向：RRF 的价值恰恰在于
[「不需要做分数标度校准就能融合异质通道」](https://arxiv.org/pdf/2606.28352)（SemEval-2026 那篇），
而朴素加权平均在异质标度上会失效
（[dense 0.89 vs sparse 0.95 不同尺度](https://medium.com/@robertdennyson/dense-vs-sparse-vs-hybrid-rrf-which-rag-technique-actually-works-1228c0ae3f69)）。

### 实测：10 种方法逐个跑

新建 `tools/_p194_calibration_probe.py`：**同一批 12 道题、同一套判据**，
只改 `score_calibration_method`，深拷贝 config 不污染生产配置。

| 方法 | r@1 | r@5 | r@10 | 判定 |
| --- | --- | --- | --- | --- |
| **none（基线）** | **83%** | **92%** | **100%** | 基线 |
| minmax | 67% | 92% | 100% | 负优化 |
| rank_percentile | 75% | 92% | 100% | 负优化 |
| robust_sigmoid | 75% | 92% | 100% | 负优化 |
| semantic_minmax | 67% | 92% | 100% | 负优化 |
| semantic_rank_percentile | 75% | 92% | 100% | 负优化 |
| **semantic_robust_sigmoid** | **83%** | 92% | 100% | 追平（不提升） |
| semantic_rrf | 67% | 92% | 100% | 负优化 |
| semantic_sparse_rrf | 67% | 92% | 100% | 负优化 |
| weighted_rrf | 67% | **67%** | 92% | 明显负优化 |

### 结论（这条最有价值）

**第 191 轮的失败不是标度问题。**

- 所有校准方法里最好的是 `semantic_robust_sigmoid`，只**追平** 83%，不提升
- `weighted_rrf` 甚至把 recall@5 从 92% 打到 67%
- 校准**只作用于 `vector_pools`（段落侧）**，改变不了 episode 通道的词法分

所以「episode 插队失败」的根因要重新理解：**不是"量纲不同所以不能混排"，
而是"混排之前没有统一的通道权重语义"**。硬要把 episode 挤到前面，
会牺牲段落通道本来准确的排序，而 episode 通道在这 12 道题上并没有提供
段落通道缺的信息（recall@10 已经 100%，说明答案都在段落里）。

### 处理

- 🔻 待办 #2 **降级**：不再作为"先做校准再说"的前置条件
- ❌ **不要**改配置切到任何校准方法（10 种里 9 种负优化）
- 📌 真要提升 recall@1，回到那两道具体题上：
  「承诺」第 9 位（承诺句长）、「称号」第 3 位（同义表述）
  —— **这是内容问题，不是排序问题**

## §3 关系双向性：先量了才知道**问题不在这里**

### 原待办写的是

> 关系类事实双向性 —— 目前单向

### 实测（新建 `tools/_p194_relation_bidir.py`，只读）

```
relations 总数: 167
完全反向重复对（A→B 与 B→A 同 predicate）: 0
单向边（找不到任何反向）: 167 / 167 = 100%
自环（A→A）: 0
object 是纯数字（其实是定量指标，不是关系边）: 18 / 167 = 11%
vector_state 分布: [('ready', 167)]
```

**100% 单向是真的**，但继续看 predicate 分布就知道为什么：

```
参与 8 | 形象包含 5 | 澄清 4 | 游玩 3 | 抽到 3 | 转发 2 | 评价 2
认为 2 | 答对硬币XOR 2 | 确认 2 | 玩 2 | 是 2 | 抱怨 2 | 开源了 2
```

**这些 predicate 天生就不该有反向边**：

- `大肥鱼 --参与--> 硬币XOR游戏`：反向是「硬币XOR游戏参与大肥鱼」，荒谬
- `DeepSeek --开源了--> DeepInfer`：反向「DeepInfer 开源了 DeepSeek」,错误
- `大肥鱼 --壳币累计达到--> 967`：这**根本不是关系**，是定量指标

按语义分组统计：**对称语义的关系只有 1 条**，其余 166 条都是天然单向的。

### 所以真正的问题是什么

**不是「缺反向边」，是「predicate 语义混杂」**：
把「定量指标」（`壳币累计达到 967`）、「一次性动作」（`转发`）、
「观点」（`评价为硬核`）全部塞进 `relations` 表，用同一套 graph 逻辑处理。

11% 的边 object 是纯数字，这类边在图上毫无意义（节点是数字 `967`），
还会污染 graph 检索和 PageRank。

### 外部资料怎么说

知识图谱领域的标准做法是**区分关系类型**：
对称关系（朋友、同事）存一条即可，遍历时按无向处理；非对称关系（教、属于）严格有向。
[GraphStore 本身就支持这种混合](D:\MaiBot\src\A_memorix\core\storage\graph_store.py#L1029)：

> 「支持有向和无向（视作双向）探索」

也就是说：**存一条 + 遍历时按需双向**，而不是**存两条**。
我们不需要给 167 条边补反向副本（那会让表翻倍，且大部分反向是语义垃圾）。

### 处理

- ✏️ 待办 #3 **改写**：从「关系类事实双向性（目前单向）」改成
  **「relations 表语义混杂：11% 是定量指标而非关系，需分流到 fact_claims」**
- ❌ **不要**批量补反向边
- 📌 短期：把 object 是纯数字的 18 条从 `relations` 移走（它们已经有对应的
  `fact_claims` 记录了，见 `_p181_test_metric_value.py`）
