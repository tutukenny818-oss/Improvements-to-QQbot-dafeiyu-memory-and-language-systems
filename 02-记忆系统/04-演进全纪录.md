## §1 （第 178 轮）补齐事务时间 `expired_at`

### 为什么改

`fact_claims` 只有「事件时间」（`valid_from` / `valid_to`），缺「事务时间」。
**后果**：回答不了「这条事实是什么时候被更正的」，只能回答「它什么时候不成立的」。
这不一回事 —— 一条 10-18 的事实可能在 10-21 才被我们发现过时。

这正是 `资料_记忆系统调研.md` 列为 **P0** 的那一项。

### 依据（Zep 论文 arXiv:2501.13956 §2.2.3 原文）

> "the system tracks four timestamps: `t'created` and `t'expired ∈ T'` monitor when facts
> are created or invalidated in the system, while `t_valid` and `t_invalid ∈ T` track the
> temporal range during which facts held true."
>
> "When the system identifies temporally overlapping contradictions, it invalidates the
> affected edges by setting their `t_invalid` to the `t_valid` of the invalidating edge."

映射：

| Zep | 我们 | 状态 |
| --- | --- | --- |
| `t'created` | `created_at` | ✅ 已有 |
| **`t'expired`** | **`expired_at`** | ✅ **本轮补** |
| `t_valid` | `valid_from` | ✅ 已有 |
| `t_invalid` | `valid_to` | ✅ 已有 |

### 改了什么

| 文件 | 改动 |
| --- | --- |
| `A_memorix/core/storage/metadata_schema.py` | 新增 `_ensure_fact_bi_temporal_columns()`，挂到 `_ensure_fact_tables()` |
| `A_memorix/core/storage/metadata_fact.py` | supersede / retract 写 `expired_at`；restore 时**清空**它 |

**语义约定**（写坏了会误导检索）：

```
active / conflicted      → expired_at IS NULL
superseded / retracted   → expired_at = 失效那一刻
```

**为什么 `paragraphs` / `relations` 不加**：它们各有 `expires_at` / `inactive_since`，
语义不同（清理 vs 生命周期），硬套会制造两套并行时间字段。

### 历史回填

38 条失效记录用 `COALESCE(updated_at, valid_to, created_at)` 回填；16 条 active 保持 NULL。

### 验证

```powershell

python -X utf8 D:\BotBackup\20261021_0550\tools\_backfill_texpired.py
python -X utf8 D:\QQBot\tools\_p175_eval.py
```

结果：字段建成 / `active 空16 共16`、`retracted 空0 共38` / 评测不掉分。

### 回滚

          'D:\MaiBot\src\A_memorix\core\storage\metadata_fact.py' -Force
```

## §2 （第 178 轮）切断「bot 被注册成人」的死循环

### 为什么改

第 177 轮把果壳 bot（`qq:BOT_B_QQ`）在 `person_info` 里标 `is_known=0`，
指望它不再被当作群友。

**但实测 2026-10-21 06:10:33 它又变回 `is_known=1`**——那一刻正是果壳在群里
发出一条 B 站视频消息的时间。

### 根因

```
果壳在群里发消息
  → heartflow_message_processor.py:94  Person.register_person(...)
  → person_info.py: is_person_known(person_id) 看到 is_known=0 → 判为"不认识"
  → 走新建分支 → person.is_known = True  (person_info.py:232)
  → 写库
```

**标 0 → bot 说话 → 变回 1**，闭环。

### 改了什么

| 文件 | 位置 | 改动 |
| --- | --- | --- |
| `src/person_info/person_info.py` | 188-200 | 新增模块级 `_is_bot_self()`（延迟导入，避免与 `chat/utils/utils.py` 循环导入） |
| `src/person_info/person_info.py` | 234-257 | `register_person()` 在新建**之前**先判 `_is_bot_self()`，是 bot 直接 `return None` |

**为什么用延迟导入**：`src/chat/utils/utils.py` 顶部会
`from src.person_info.person_info import Person`，本模块要反向调它的 `is_bot_self`。
顶层互相 import 会循环导入。延迟导入只在真正注册新用户时发生，开销可忽略。

**边界**：`Person.__init__` 里对 bot 的处理是另一套（`is_known=True` 且昵称取
`global_config.bot.nickname`），那是给「机器人自己」用的，与「注册一个陌生 user_id」不是同一件事，没动。

### 怎么验证

```powershell
python -X utf8 D:\BotBackup\20261021_0550\tools\_verify_botfix.py
```

实测输出：
```
_is_bot_self('qq','BOT_B_QQ')      -> True     （果壳 bot）
_is_bot_self('qq','1234567890')      -> False    （陌生人）
先标 is_known=0 → 调 register_person → 返回 None
注册后 is_known = 0   ✅ 守住了
```

数据库状态同步修正：`person_info` 里「果壳」`is_known=0`（全库唯一一条 0）。

### 回滚

```powershell
Copy-Item 'D:\BotBackup\quarantine_20261021\person_info.py.before_botfix_20261021_070921' `
          'D:\MaiBot\src\person_info\person_info.py' -Force
```

### 还剩什么

- **两条独立的路**要分清：`bot_platform_accounts.disabled=0` 管「记忆写入拦截」
  （`is_bot_self` 走这条），`person_info.is_known` 只管「人物表登记」。
  前者一直是有效的，后者才是本轮修的。
- `person_info` 里果壳那行**保留着**（没删），只是 `is_known=0`。这是有意的：
  保留行避免外键/历史引用断裂，靠 `is_known` 表达"不是人"。

## §3 （第 178 轮·续）从「能检索到」到「记得准」

> 上一节（§1）补完 `expired_at` 后，我按承诺把评测从 9 题扩到 30 题。
> **一扩就炸**：24/30。下面每一次修复都对应一个**实测出来**的缺陷。


### 3.1 评测扩到 30 题 —— 先让它失败

| 类别 | 题数 | 设计意图 |
| --- | --- | --- |
| user_fact | 5 | 人物事实，不能串人 |
| preference | 3 | 偏好，主语必须对 |
| knowledge_update | 4 | 数值类，不能返回矛盾值 |
| temporal | 6 | 时间锚定 |
| multi_session | 5 | 跨天/跨会话 |
| assistant_info | 3 | 关于 bot 自己 |
| **temporal_gap** | 4 | **新增：专抓「没存时间」** |

`temporal_gap` 这 4 题是用户原话场景：「昨天凌晨三点我在干嘛」。
**旧 9 题全过，但这 4 题全炸** —— 说明旧题集**掩盖**了「记不住时间」这个大问题。



### 3.2 缺陷 1：评测本身设计错（不是记忆错）

**现象**：问「昨天凌晨 3 点」，语义 Top-5 被那天更"像"的摘要挤掉。

**原因**：评测只按余弦相似度取 Top-K，**没复现真实链路**。
真实的大肥鱼在用户明确说时间时，会带 `time_start/time_end` 去查。

**修法**：给题加 `window: (start_epoch, end_epoch)`，
评测里先按时间窗取、再并上语义 Top-K。

**效果**：temporal 4/6 → 6/6、temporal_gap 3/4 → 4/4。

> 这一条**没有改产品代码**，改的是评测。
> 教训：评测不复现真实链路，测出来的"失败"可能是假的。


### 3.3 缺陷 2：66 条段落 `event_time` 为空

**现象**：段落只有 `event_time_start/end`，没有单点 `event_time`。

**根因**：`metadata_store.backfill_temporal_metadata_from_created_at()`
**早就写好了，但全项目零调用**。

**修法**：用 `start/end` 的中点补 `event_time`（66 条全部补齐，0 条缺失）。

> 为什么不用 `created_at` 兜底：`created_at` 是"我们什么时候写进库的"，
> `event_time` 是"这件事什么时候发生的"。摘要按 36 条一批写入，一批可能横跨几小时，
> 用 `created_at` 会把时间整体后移。


### 3.4 ★ 缺陷 3：27 条真人事实被误判为「死段落」

**这是本轮最严重的发现。**

```
果壳的壳币数量为972      → retracted
大肥鱼的称号是果壳常客    → 死段落，检索时被过滤
过客的壳币数量为138      → 死段落，检索时被过滤
```

**完整链条**：

1. 果壳 bot 播报 `🪙 果壳钱包 · 大肥鱼  壳币：972`
2. 抽取模型把主语写成 **「果壳的」**（其实是大肥鱼的钱包）或 **「他的」/「目标人物的」**（代词）
3. 这些 claim 挂在 **bot 的 person_id** 下
4. 第 177 轮把 bot 标记为"不是人" → 它的 31 条 claim 在 `04:50:56` 被**批量撤回**
5. 这 27 条段落的**全部证据失效** → `list_paragraphs_with_inactive_fact_claims` 判死 → 检索时整段过滤
6. **真人事实陪葬**

**我试过恢复，但结论是「没有一条能安全恢复」**：
- 21 条主语是「果壳的」→ 确实是 bot 属性，该撤
- 17 条主语是「他的」「目标人物的」→ **代词，指代不明**

**代词指代不明 = 低质量记忆**。恢复只会让模型猜错人（第 172 轮的历史错误）。
所以**不改删除逻辑**（它是对的），转而**修写入源头**。


### 3.5 修法：主语必须是具体人名

**改动 1 · prompt 加"播报场景"规则**（`memory_flow_service.py` 提取 prompt）

新增一整段，明确告诉模型：

```
🪙 果壳钱包 · 大肥鱼  壳币：972
「你」不是目标人物，是钱包所有者；「大肥鱼」才是所有者。
```

并加硬规则：**主语必须是具体人名，不允许「他 / 她 / 目标人物 / 对方 / 你」**。

**改动 2 · 代码兜底**（新增 `_fact_subject_is_pronoun`）

就算模型仍写出代词主语，写入前也拦下来：

```python
if self._fact_subject_is_pronoun(fact):
    logger.info("丢弃主语是代词的人物事实（指代不明）")
    continue
```

只匹配**句首**（中文里句首才是主语位），所以「Tutu喜欢他」这种宾语位不会被误杀。
**单元测试 10/10 通过**。


### 3.6 缺陷 4：摘要窗口按「条数」而不是「时间」

**现象**：记忆库里有摘要跨度 **15.5 小时**（`10-20 01:52 → 17:25`）、**18.6 小时**（`10-19 00:26 → 19:01`）。

**根因**：`chat_summary_writeback_message_threshold = 36` —— **36 条消息**触发一次。
群聊稀疏时，36 条能横跨半天。

**后果**：凌晨 3 点说的话被合并进一条巨型摘要，摘要正文里不会提到它，
问「昨天凌晨 3 点我做了什么」**永远检索不到**。

**依据**（按硬约束先去查）：
[Pinecone《Chunking Strategies for LLM Applications》](https://www.pinecone.io/learn/chunking-strategies/)：
> 分块要"大到含有意义、小到能精确检索"；固定大小不够时，
> 聊天类内容应按**时间或话题边界**切分。

我们已有条数边界，缺时间边界。

**修法**（三处）：

| 文件 | 改动 |
| --- | --- |
| `config/official_configs.py` | 新增 `chat_summary_writeback_max_window_hours`，默认 **2.0 小时**，0 = 不限 |
| `services/memory_flow_service.py` | 算 `time_start = message_time - N 小时`，塞进 metadata |
| `A_memorix/core/utils/summary_importer.py` | `get_messages_by_time_in_chat(start_time=...)` 用上它 |

**兜底**：窗口内一条消息都没有时（群太久没说话）**退回旧行为**，
宁可摘要粗一点，也不要"这条时间窗永远不产生记忆"。

**踩的坑（诚实记录）**：我想把这个配置也写进 `bot_config.toml`，
用 PowerShell 改文件时**把 TOML 写坏了**（`TOMLDecodeError: Invalid statement`）。
立刻从备份回滚，验证 25 个节全部正常。
**结论：不写进 toml 也能用**（有代码默认值 2.0），所以最终**没改那个文件**。
教训：**改 TOML 要用 Python 读写，不要用 PowerShell 拼字符串。**


### 3.7 ★ 恢复 27 条被误归属的真人事实（本轮最后一步）

**发现**：那 27 条「死段落」的**正文是写对的**，只有 claim 的 `value_text` 被写成了代词/错误主语：

```
段落（正确）：大肥鱼的壳币数量为972
claim（错误）：果壳的壳币数量为972        ← 主语被写成 bot
```

**所以可以恢复，而且不算伪造** —— 用**段落原文**去纠正 claim，不是凭空生成。

**规则**（严格）：

| 段落以…开头 | 归属 |
| --- | --- |
| `大肥鱼…` | 大肥鱼的 person_id |
| `过客…` | 过客的 person_id |
| 其他 | **跳过**（宁缺勿滥） |

**执行**：27 条全部恢复（0 跳过），同时记 `fact_transitions(transition_type='restore')` 留审计痕迹。

**结果**：

```
active     16 → 43
retracted  38 → 11   （剩下的全是"该撤"的：bot 属性 / 代词指代不明 / 已知误判）
死段落     27 → 0
```


### 3.8 顺带修掉 1 条代词主语

`目标人物很喜欢大肥鱼`（scope = 我是空气）→ 按证据段落改为 `我是空气很喜欢大肥鱼（说过 1 次）`。

复查：**active 事实里代词主语 = 0 条**。


### 3.9 ★ 上游 bug：`_relation_vector_backfill_loop` 只有调用没有定义

**发现**：`relations` 表 118 条全部 `vector_state='none'`（从未建向量），
关系检索只能靠 FTS 关键词。

**根因**：`lifecycle_orchestrator.py:143` 调用 `plugin._relation_vector_backfill_loop()`，
但**全包没有这个方法的定义**（同类的 `_paragraph_vector_backfill_loop` 有）。

**所以 `relation_vectorization.enabled = true` 会直接 `AttributeError` 崩启动。**
这也解释了为什么配置里一直是 `false` —— 开了就崩，只能关着。

**处置（按 AGENTS.md 约束 1b）**：
- **没有强行实现**（改上游实现层受 MODIFICATION_POLICY 约束）
- **写了 issue 草稿**：`docs\upstream-issues\a-memorix-relation-vector-backfill-loop-missing.md`
- 本地保持 `enabled=false`，功能不退化

**验证过的判断**：即便补上关系向量，**也解决不了当前那 1 道失败题** ——
因为「大肥鱼喜欢催睡觉」这个**关系在抽取阶段就没被建出来**，
不是检索找不到，是库里压根没有。所以不急着做。

本轮 30 题里那 3 道「失败」，**正确答案其实一直躺在库里**，

### 3.10 ★ 实体解析前置（P0-2）已落地

**依据**（先查再做）：
- Zep arXiv:2501.13956 §2.2.1 的顺序是 `extract entities → entity resolution → extract facts`
- LINK-KG arXiv:2510.26486 也是三阶段、**指代消解在前**
- 我们原来是反的：先抽事实，模型自己猜主语

**改了什么**（`src/services/memory_flow_service.py`）：

新增 `_build_entity_candidates()` —— 在抽取 prompt **之前**生成候选实体清单：

```
**本段对话里出现过的人（主语只能从这里选，不要自己编名字）：**
  - Tutu：目标人物
  - 大肥鱼：机器人（不是人，不能作为事实主语）
  - 果壳：机器人（不是人，不能作为事实主语）
```

再加 `_known_other_bots()` —— **从 `bot_platform_accounts` 表读**，不读 `.env`。
理由：`.env` 是果壳那边的约定，大肥鱼根本不 `load_dotenv`；
而 `bot_platform_accounts` 是两个 bot 都认的真相来源（第 177 轮已登记果壳）。

**为什么用启发式而不是再调一次 LLM**：再调一次 = 每条消息多一次调用，
成本翻倍且引入新出错点。群里能当事实主体的就那么几个，三类候选够用。

**端到端验证**（真实调用模型，非模拟）：

| 场景 | 结果 |
| --- | --- |
| A. 用户自述「我最喜欢白米饭」「我平时爱玩24点」 | ✅ 抽出 2 条，`subject=Tutu` |
| B. bot 播报 + 用户说话（历史出错场景） | ✅ **抽出 0 条** —— 不再把 bot 播报误写成用户事实 |

**场景 B 从「写出错误事实」变成「一条也不写」**，正是想要的效果：**宁可少记，也不记错**。

### 3.11 ★ 补上缺失的 `_relation_vector_backfill_loop`，关系语义通道打通

## §6 （第 179 轮）修上一轮自己造成的 `conflict_group` 失配

### 6.1 怎么发现的

复查时问了一句「大肥鱼到底有多少壳币」，人物画像里同时返回三条：

```
大肥鱼当前拥有壳币 767
大肥鱼自称常客，已连续3天出现，壳币为547
大肥鱼的壳币数量为972
```

三条都是 `status='active'`、`stability='stable'`、同一个 `fact_key`
（`metric:...:guoke.shell_coin`）。按设计只该留最新那条。

### 6.2 根因（**是第 178 轮我改出来的**）

`conflict_group` 的算法是：

```python
hash(scope_type, scope_id, fact_key)     # cardinality != 'set'
hash(scope_type, scope_id, fact_key, value_normalized)  # cardinality == 'set'
```

`scope_id` 在哈希里。第 178 轮把 27 条误挂在 bot 名下的事实搬回真人名下时，
**改了 `scope_id`，没重算 `conflict_group`**。

实证（用备份快照对比）：

| 时点 | scope_id | conflict_group 前 12 位 |
| --- | --- | --- |
| 05:50 备份 | `0c34de53…`（果壳 bot） | `f96e5f7cf7db` |
| 现在（大肥鱼） | `818fe520…` | 本应 `1d2f2add56b8`，实际仍是 `f96e5f7cf7db` |
| 现在（过客） | `ddd79dca…` | 本应 `03967d0ad820`，实际仍是 `f96e5f7cf7db` |

验证：把 `scope_id='0c34de53b52475a0339bac6835f4b83c'`（bot）代进
`_conflict_group()`，算出来的正好是 `f96e5f7cf7db`。**完全对上。**

### 6.3 后果链

```
conflict_group 错
  → upsert_fact_claim 查「同组有没有别的 active」查不到
  → 永远不触发 supersede、也不标 conflicted
  → 同一个人的同一个指标无限累积
  → 检索时 767 / 547 / 972 一起返回，模型只能猜
```

全库统计：54 条 claim 里 **30 条** conflict_group 失配（其中 active 的 39 条里占绝大多数）。

### 6.4 修法

脚本 `tools/_p179_fix_conflict_group.py`：

1. sqlite backup API 在线备份（不锁生产）
2. 逐条按 `(scope_type, scope_id, fact_key, cardinality, value_normalized)` 重算
3. 只 UPDATE 不一致的
4. 二次全量校验

结果：**30 条修正，0 条残留不一致**。

### 6.5 紧接着暴露的第二层：历史重复 claim

`conflict_group` 修好只对**以后新写入**生效。库里的历史垃圾还在。
用生产代码自己的 `fact_metrics.should_supersede` 补做一次判定（不自己发明判据）：

改动 6 条，全部有据：

**剩下 4 组故意不动**（`Tutu喜欢对方`/`Tutu喜欢大肥鱼`、三份「果壳常客」称号、

## §7 （第 179 轮）定性事实去重：补上一个从没被填过的洞

### 7.1 怎么发现的

§6 清理数值重复时，用 `should_supersede` 判定，剩 4 组故意没动。
复查那 4 组的具体内容，发现其中三条是**同一个事实换了句式**：

```
大肥鱼的称号是果壳常客        ← 同一件事
大肥鱼的称号是“果壳常客”      ← 同一件事（只差引号）
大肥鱼拥有“果壳常客”称号       ← 同一件事（句式不同）
```

```
过客拥有“果壳元老”称号        ← 一字不差的重复
过客拥有“果壳元老”称号
```

这不是「一个人有好几个称号」的正常情况，是**纯冗余**。
它们挤占召回名额，还会让模型以为「有好几个不同的称号」。

### 7.2 根因

`should_supersede` 里写着：

```python
if new_value is None:
    # 抠不出数值（比如"称号是果壳常客"），保守：不取代。
    return False, "新值无可比数值"
```

**这个决定是对的**（一个人确实可以有好几个称号），但它留了一个洞：
连「一字不差的重复」也进不来。

也就是说：**定性事实这条路上，从来没有任何去重机制。**

### 7.3 依据（外部资料）

- [Senzing · Entity Resolved Knowledge Graphs](https://senzing.com/entity-resolved-knowledge-graphs/)：
  entity resolution 的核心是「**先把同一断言规范到可比形式，再判等**」，
  不能直接比原始字符串。
- [Zep 论文 arXiv:2501.13956](https://arxiv.org/html/2501.13956v1)：
  事实去重前先做实体解析，顺序不能颠倒。

**结论**：先做归一化指纹，再判等。不需要 ML ——
中文里这类重复的差异**几乎全在措辞模板**上。

### 7.4 实现

`fact_metrics.py` 新增两个函数：

| 函数 | 作用 |
| --- | --- |
| `qualitative_fingerprint(text)` | 把陈述压成可比较的骨架 |
| `is_same_qualitative_fact(a, b)` | 指纹完全相同才判「同一件事」 |

归一规则（顺序固定，保证幂等）：

1. 全角转半角、去空白（复用 `normalize_metric_text`）
2. 去标点（引号/书名号/括号/逗号句号）
3. **谓语模板归一** → 统一成 `主语 + 谓词骨架 + 宾语`
4. 去句末语气助词
5. 小写化

第 3 步踩了个坑：**「拥有」不能简单替成「有」**。

```
大肥鱼拥有“果壳常客”称号  --(拥有→有)-->  大肥鱼有果壳常客称号     ← 称号在末尾
大肥鱼的称号是“果壳常客”  ----------->  大肥鱼称号果壳常客       ← 称号在中间
```

骨架不同就匹配不上。正确做法是用正则把 `拥有X称号` **整体重排**成 `称号X`：

```python
out = re.sub(r"拥有(.+?)称号", r"称号\1", out)
```

另外钱包名那条的差异在修饰语（「的果壳」vs「在抓壳游戏中的」），
对判「是不是同一个钱包名」没有信息量，模板里统一吃掉。

### 7.5 接入生产写入链路

`ingest_service._write_person_fact_claims` 里，原来的分支只处理有数值的：

```python
if not supersedes and cardinality == "single" and looks_like_metric_value(statement):
    supersedes = self._find_superseded_claims(...)
```

新增一条**并列**分支（`if not supersedes:`，优先让数值判定先生效）：

```python
if not supersedes:
    supersedes = self._find_duplicate_qualitative_claims(...)
```

新方法 `_find_duplicate_qualitative_claims` 的文档里写清了边界：
**指纹相同 → 合并；指纹不同 → 一律不动**。
宁可漏合并（白占一个名额），也不能错合并（凭空删掉一个真实称号）。

### 7.6 验证（三层，缺一不可）

## §8 （第 179 轮）建严评：30/30 的评测已经没有区分度

### 8.1 为什么要再建一个评测

`_p175_eval.py` 是 **30/30 全绿**。全绿的评测没有区分度 ——
它测不出「再改一步会不会变差」，也就没法指导下一步做什么。

三个结构性弱点（真实查过）：

| 弱点 | 具体表现 |
| --- | --- |
| 判定靠关键词命中 | `must_have: ["972"]` —— 972 出现在任何一条召回里就算过，哪怕同一条还有 767 |
| 自己重写检索逻辑 | 手写 `cosine` + 手写窗口。改产品代码，评测不一定跟着变 |
| 没有反向题 | 从不问「库里根本没有的事」，测不出**幻觉** |

### 8.2 建的过程踩了三个坑（全是「尺子量错了」）

**坑 1：`MemoryService` 拿不到锁**

它走 `a_memorix_host_service.invoke()`，是**跨进程 IPC**。
停掉大肥鱼后 `src.runtime` 也没了，IPC 永远等不到回应 →
每题返回空，看起来像「记忆全丢了」。

**修法**：直接复刻 `host_service._startup_kernel_task()`：
`SDKMemoryKernel(plugin_root, config)` + `await initialize()`，
进程内独占锁。

**坑 2：读错返回字段**

`search_memory` 返回 `dict`，键名是 **`hits`** 不是 `results`。
读 `results` 永远拿不到 → 15 题全「空」。

**坑 3：向量通道是关着的**

第一次跑出来 `unavailable_channels: ['vector_read', 'vector_write']`，
`degraded=True` —— 检索完全没走向量。

原因（`embedding_state_service.py:364-396`）：单池加载要用
`_current_embedding_fingerprint_for_validation()` 校验旧向量世代，
而那个指纹**必须先发过一次真实 embedding 请求才有值**。
没发过 → 指纹 `None` → 抛 `embedding_fingerprint_unavailable` → 通道关闭。

**修法**：调一次 `kernel._recover_embedding_once()`。
生产里这步由后台任务触发，所以线上是好的；断点脚本必须自己补。

修完：`unavailable_channels: []`，`degraded: False`。

### 8.3 严评的设计

| 设计 | 做法 |
| --- | --- |
| 走真链路 | 调真实 `SDKMemoryKernel.search_memory()` |
| LLM 判定 | 把召回交给模型，问「能不能回答」，要 `yes/no` + 引用原句 |
| 反向题 | 故意问库里没有的事（银行卡密码 / 生日 / 猫名），答「能」就是幻觉 |
| 复现 prompt 形状 | 拼成 `1. [昨天 03:13] 内容` —— 与生产同一条渲染路径 |

题集 15 题分 5 类：fact / attribution / temporal / multihop / absent。

### 8.4 第一次真跑：12/15，暴露三个真实缺陷

```
[x] [attribution] 过客的壳币有多少  ← 多个互相矛盾的壳币旧值
[x] [temporal] 最近一次提到 ipynb 是什么时候  ← 没有任何时间戳
[x] [temporal] 大肥鱼什么时候说过要催大家睡觉  ← 未提及具体时间
```

**三道失败里有两道是同一个根因：召回内容里没有时间。**

数据层是好的（109 条段落有 `event_time`、80 条有 `event_time_start/end`），
但 kernel 这条路径**从来没把它带出来**。

## §9 （第 179 轮）★ 修 `time_meta` 丢失：记忆有时间，但模型看不到

### 9.1 现象

问「最近一次提到 ipynb 是什么时候」，召回内容正确，但模型答：

> 检索内容提到 ipynb 报错原因，但未给出「最近一次提到」的具体时间信息，无法回答。

### 9.2 链路追踪

```
memory_service._coerce_search_result  ← 从 metadata.time_meta 渲染 time_text
        ↑
MemoryHit.time_text
        ↑
memory_service:221 / heuristic_injector:407  ← 拼成 `1. [昨天 03:13] 内容`
```

链路**是完整的**（第 168 轮就写好了）。问题是 `metadata.time_meta` **压根不存在**。

实测三个 hit 的 metadata 键：

```
['word_count', 'score_breakdown', 'evidence_items', 'dual_pool_sources']
```

没有 `time_meta`。

### 9.3 根因

`_retrieval_result_hit`（`search_hit_processing_service.py:893`）直接取
`RetrievalResult.to_dict()` 的 metadata。而向量库回来的 `RetrievalResult`
**不携带时间字段**。

对比 `dual_path.py` —— 那边有 6 处主动调
`_build_time_meta_from_paragraph()` 补上。**kernel 这条路径一处都没有。**

更糟的是 `search_execution_service.py:434`：

```python
if "time_meta" not in metadata:
    metadata["time_meta"] = {}
```

塞空 dict 会把「没查」伪装成「查过了，确实没时间」——
掩盖了整整一轮。

### 9.4 修法

在 `memory_search_service._finalize_search_response()` 里补 `_attach_time_meta()`。

**为什么放这里**：它是 search / episode / aggregate **三种模式共同的唯一出口**。
放这里一次覆盖全部，不用每个分支各补一遍（也不会漏）。

```python
# 按 hash 批量查库，比逐条查省
rows = store.get_paragraphs_by_hashes(list(hash_to_item.keys()))
# 产出与 dual_path._build_time_meta_from_paragraph 对齐的形状
metadata["time_meta"] = {
    "effective_start": ..., "effective_end": ...,
    "match_basis": "event_time_range" | "event_time",
    ...
}
```

三个设计决定：

1. **拿不到就什么都不加**，绝不塞空 dict —— 空 dict 会掩盖问题
2. **已经有就不覆盖** —— 上游可能给了更精确的
3. **异常全吞** —— 补不上时间只是少个标签，不能让整次检索失败

### 9.5 效果

修之前：`time_meta: MISSING`（0/5 有时间）
修之后：

```
[昨天 14:19~15:51] 哈机密果壳的 ipynb 作业运行报错...
[昨天 15:07~16:02] 本时段群内讨论主要围绕《我的世界》...
[昨天 14:21~15:53] 哈机密果壳的 ipynb 作业运行报错确认...
[昨天 15:07~16:02] 本时段讨论主要围绕《我的世界》...
[昨天 15:52~18:04] 本时段群聊涉及《我的世界》...
有时间标签: 5/5
```

严评：`12/15 → 14/15`。两道时间题双双转绿：

```
[v] [temporal] 最近一次提到 ipynb 是什么时候
     依据: [昨天 14:19~15:51] 哈机密果壳的 ipynb 作业运行报错...
[v] [temporal] 大肥鱼什么时候说过要催大家睡觉
     依据: [昨天 03:13~07:04] 大肥鱼确认自己喜欢做的事就是催群友早点睡觉
```

### 9.6 教训

**「第 168 轮写过」≠「它一直在工作」。**
时间渲染代码写了整整 11 轮，但因为上游从没给过 `time_meta`，
它**从来没生效过**。

而且它失效得毫无痕迹 —— 因为 `time_text` 是空串，
空串在 prompt 里看起来就像「这条记忆本来就没有时间」。

## §10 （第 179 轮）★ 记忆断流：第 178 轮的 prompt 把抽取率压死了

### 10.1 现象（比前两条严重得多）

查「过客有多少壳币」时发现：**过客的事实层全部停在 10-20 01:32**，
之后 30 多个小时**一条新事实都没有**。

而段落里明明记录了 216 → 258 → 368 → 547 的变化。

再查全库：

```
10-21 的 17 个段落，产出的事实 = 0 条
person_fact 段落最后一次写入 = 10-21 04:53:29
之后 8 小时无新增
```

**事实抽取整条链路是死的。**

### 10.2 定位过程

| 假设 | 结果 |
| --- | --- |
| 配置开关关了 | ❌ `person_fact_writeback_enabled=True` |
| `is_known` 把人都挡了 | ❌ 34 人 `is_known=1`，过客/Tutu 都在 |
| 日志里有「丢弃」记录 | ❌ 全库日志 0 命中 |
| 大肥鱼没发过言所以没触发 | ❌ 摘要还在正常写入，说明触发过 |

那就直接测抽取函数本身：

```python
facts = await _extract_facts(svc, FakePerson("过客"),
                             "过客说自己壳币 368",
                             "[目标用户发言] 我今天壳币 368 了")
# → 条数: 0
```

**用用户自述最明确的证据，抽取结果是 0 条。**

### 10.3 消融实验：是 prompt 太长

同一证据（「我今天壳币 368 了」），各跑 5 次：

| prompt | 抽取率 |
| --- | --- |
| **长 prompt（第 178 轮版，约 1200 字）** | **1/5** |
| 短 prompt（约 200 字） | 3/5 |

短的抽取率是长的 **3 倍**。

第 178 轮为了修「主语写错」，往 prompt 里堆了：

- 人称规则 3 行
- 「真实错误」对照表 3 行
- 播报格式对照表 3 行
- 硬规则 3 条
- 「请只提取」7 条
- 「不要提取」7 条
- 输出格式说明

模型被「不要」淹没了 —— 它把「宁可少记一条」执行得**过火**，
干脆一条都不记。

这与 §0 资料清单里那篇双过程记忆论文的结论完全一致：
「consolidation 的瓶颈在 **prompt 设计**，不在模型能力」
（arXiv:2605.17625 §5.4：换更强的模型准确率只涨 0.07%）。

### 10.4 第二个缺陷：JSON 解析吞掉了结果

实测同一 prompt 跑两次，模型有时返回

```
[{"fact": "...", "subject": "..."}]
```

有时返回

```
```json
[{"fact": "...", "subject": "..."}]
```
```

`json_repair` 对围栏的处理**不稳定**（有时能救、有时不能），
而解析失败会被 `except` 吞掉返回 `[]` ——
上层看到的是「模型认为没有事实可记」，于是静静什么都不写。

### 10.5 修法

**① 解析器加固**（`_parse_fact_items`）：

```
1. 剥掉 ```json ... ``` / ``` ... ```
2. 直接 json.loads
3. 失败 → 截取最外层 [ ... ] 再试
4. 再失败 → json_repair 兜底
```

**② 空结果重试一次**：

```python
items = self._parse_fact_items(response_result.response)
if not items:
    # 模型输出有随机性，同一 prompt 有时吐 [] 有时吐完整 JSON
    retry = await self._extractor.generate_response(prompt + "（上一次返回空，请再看一遍）")
    items = self._parse_fact_items(retry.response)
```

只在**空结果**时才多发一次，正常有结果不增加开销。

**③ prompt 瘦身**（关键修复）：

保留真正必要的三件，其余删掉：

| 保留 | 理由 |
| --- | --- |
| 代词规则（「我」= 目标人物，「你」= 机器人） | 这是事故根源，必须留 |
| **正例**（该记什么） | 比反例有效 |
| 播报场景一句话提醒 | 真踩过的坑 |

删掉：「不要提取」清单（模型本来就保守）、大部分反例表格、
7 条并列条件里 4 条重复表述。

### 10.6 验证

**新 prompt 逐场景验证，每个跑 3 次**：

| 场景 | 结果 |
| --- | --- |
| 用户自述壳币 | ✅ 3/3 → `过客的壳币数量为 368` |
| 用户说口头禅 | ✅ 3/3 → `Tutu的口头禅是正经点` |
| 用户说爱好 | ✅ 3/3 → `过客最近一直在玩硬币游戏` |
| **播报归属**（第 178 轮的 bug） | ✅ 3/3 → `大肥鱼的壳币数量为972`（没复现错误） |
| 闲聊（该返回空） | ✅ 3/3 → `[]` |
| **「你有听觉吗」**（该返回空） | ✅ 3/3 → `[]`（没把机器人属性记到人头上） |

**6/6 场景全绿，且两个反例都正确返回空。**

**解析器**：`tools/_p179_test_fact_parser.py` **16/16**
（8 种「该解析出来」+ 6 种「该返回空」+ 坏 JSON 不抛异常 + 5 条上限保护）

**全量回归**：

| 项 | 结果 |
| --- | --- |
| `_p175_eval.py` | **30/30** |
| `_p179_test_fact_parser.py` | **16/16** |
| `_p179_test_qualitative.py` | **17/17** |
| `_p179_e2e_qualitative.py` | **5/5** |
| 大肥鱼重启 | 8 进程 / 0 error |

### 10.7 教训（这条最重要）

**修一个 bug 时加的每一句「不要」，都在削弱系统的另一半能力。**

第 178 轮加那堆规则的目的是「不要让主语写错」，
代价是「干脆什么都别记」。而且这个代价**在当时完全看不出来** ——
因为评测 30/30 全绿，没有任何指标在监控「每天记了多少条事实」。

**缺的不是规则，是监控。** 如果早有一个「每日新增事实数」的曲线，
10-21 上午就会发现它掉到 0 了，而不是等到查一个具体问题才发现。

这也再次印证 §8.1：**没有区分度的评测会掩盖真实故障。**

## §11 （第 179 轮）加健康监控 + 顺手挖出「死段落」判定错误

### 11.1 为什么要加监控（承接 §10.7）

§10 的教训是「缺的不是规则，是监控」。所以补一个：
`tools/_p179_memory_health.py`，9 项检查：

| 检查 | 阈值 | 抓什么 |
| --- | --- | --- |
| DB 完整性 | `ok` | 库坏了 |
| **24h 新增段落** | > 0 | 摘要链路死了 |
| **24h 新增事实** | > 0 | **抽取链路死了**（§10 踩的就是这个） |
| **事实/段落比** | ≥ 0.10 | 抽取在空转 |
| **最新事实年龄** | < 36h | 抽取停了 |
| **死段落** | == 0 | 事实被误撤 |
| 关系向量 ready | == 100% | 回填停了 |
| 段落无任何时间 | 报告 | 时间定位失效 |
| 重复事实组 | 0 | 检索会返回矛盾值 |

设计原则：**阈值放松，只抓「链路整体死掉」**，不报「今天比昨天少记两条」——
否则会变成噪音，最后没人看。

### 11.2 监控刚装上就抓到一个真问题

```
[x] 死段落   21 段
```

第 178 轮我说过「死段落 27 → 0」。现在又出现 21 个。

### 11.3 追踪：其中 12 个是我这轮修出来的

拆开看：

```
del=1  9 条  段落本身已删除（无所谓）
del=0 12 条  ★ 段落活着，但唯一 claim 被 superseded → 整段判死 → 检索过滤
```

那 12 条是：

```
大肥鱼当前拥有壳币 767。
大肥鱼自称常客，已连续3天出现，壳币为547
大肥鱼的连续抓壳天数为 3 天。
大肥鱼的果壳钱包名称为"大肥鱼"。
大肥鱼的图鉴收集进度为17/62种
大肥鱼的称号是果壳常客
过客的壳币数量为138
过客的连续抓壳天数为30天
过客拥有"果壳元老"称号
...
```

**全是 §6.5 / §7.6 里我自己 supersede 掉的那些。**

### 11.4 根因：把两个语义完全不同的状态混为一谈

`list_paragraphs_with_inactive_fact_claims()` 原判定：

```python
# 全部 claim 都在 {superseded, retracted} → 段落失效
if total_claims > 0 and live_claims == 0:
    dead.add(paragraph_hash)
```

| 状态 | 含义 | 段落该不该作废 |
| --- | --- | --- |
| `retracted` | 这条事实是**错的**（主语搞错 / 事实不成立） | ✅ 该作废 |
| `superseded` | 这条事实被**更新的值替代**了 | ❌ **不该作废** |

「大肥鱼当前拥有壳币 767」被 972 取代了，但
**「10-20 那天她是 767」是真实发生过的历史**。
丢弃它，问「壳币涨过几次」就答不出来。

而且这个 bug 有个恶性的自我强化：
**我越努力去重，被判死的段落就越多。** 修 §7 反而制造了 §11。

### 11.5 修法

```python
# 只有「确实有被撤回的」才判死
if retracted_claims > 0:
    dead.add(paragraph_hash)
```

`live_claims > 0` → 跳过（有有效事实）
`live_claims == 0 and retracted_claims > 0` → 判死（**确实撤错了**）
`live_claims == 0 and retracted_claims == 0`（全是 superseded）→ **保留**

### 11.6 验证

`tools/_p179_test_dead_paragraph.py`（在真实库上跑，**5/5**）：

| 分类 | 数量 | 期望 | 结果 |
| --- | --- | --- | --- |
| 只有 superseded | 10 | **不**判死 | ✅ 误判 0 |
| 有 retracted 且无 active | 11 | 判死 | ✅ 判死 11 |
| 有 active | 33 | 不判死 | ✅ 误判 0 |
| 没关联 claim | 81 | 不判死 | ✅ 误判 0 |
| **全量一致** | — | 判死集合 == 应死集合 | ✅ **完全一致** |

健康检查：`死段落 21 段 → 0 段活着但事实全被撤回`。

### 11.7 顺手修的：监控脚本自己也犯了同样的错

第一版监控脚本的 SQL 写的是 `HAVING total > 0 AND live = 0` ——
**跟产品代码的旧 bug 一模一样**。所以修完产品代码后它还在报 21。

**尺子必须跟产品用同一套语义。** 已把 SQL 对齐成
`total > 0 AND live = 0 AND retracted > 0`，并额外排除「段落本身已删」。

### 11.8 教训

**修 bug 会制造新 bug，而且新 bug 往往藏在旧 bug 的修复里。**

§7 的定性去重是对的（同义说法确实该合并），
但它暴露了 §11.4 的判定错误。如果没有 §11.2 的监控，
这 12 个段落会一直静默地从检索里消失 ——
**和 §10 的断流一样，没有任何指标会告诉你。**

## §12 （第 179 轮续）`last_known_time` 从没被读回：一个自我维持的 NULL

### 12.1 现象

`person_info` 35 条记录，`last_known_time` **全部是 NULL**。
所以「谁最近活跃」这类排序完全不可用。

### 12.2 根因：读写不对称形成的死循环

```python
# 写入端（sync_to_database，第 536 行）
last_known_time = datetime.fromtimestamp(self.last_know) if self.last_know else None
```

而 `self.last_know` **只在 `register_person()` 里赋过值**。
`load_from_database()` 从来没读过这一列。

于是：

```
load（last_know = None）→ sync（写 NULL）→ 库里 NULL → load（还是 None）→ …
```

**老用户永远拿不到时间，而且每次 sync 都把 NULL 又写回去一遍。**

### 12.3 修法（三处）

| 位置 | 改动 |
| --- | --- |
| `load_from_database` | 把 `record.last_known_time` 读回 `self.last_know` |
| `sync_to_database` | `last_known_time is not None` 才写（**只增不减**，防别的代码路径带 None 抹掉） |
| `__init__` 两个早退分支 | 补齐 `last_know` / `know_times` / `know_since` / `memory_points` 等默认值 |

第三处是顺手发现的：bot 分支和「未知用户」分支提前 `return`，
没设这些属性，任何 `person.last_know` 读取都会抛 `AttributeError`
（而不是拿到安全默认值）。

### 12.4 补历史数据

代码修了，**库里的 NULL 不会自己长出来**。
`tools/_p179_backfill_lastknow.py` 用 `mai_messages` 里该用户
**最后一条消息时间**回填 —— 语义与「最后一次被认知」基本一致。

拿不到消息的不动（保持 NULL），绝不编造。

结果：**13 条回填，NULL 35 → 0**。

### 12.5 教训

**读写不对称是最隐蔽的一类 bug。** 单独看 `load` 没问题，单独看 `sync` 也没问题，
只有把两条路径并排放，才看得出"写出去的值永远读不回来"。

而且它会**自我维持** —— 每一次正常的 sync 都在加固这个错误状态，
所以不会自己好转。

## §13 （第 179 轮续）事实抽取其实没坏：是"没有可记的内容"

## §17 （第 180 轮）★ episode 层建好了，但一个字节都没进过 prompt

### 17.1 先纠正当年的判断

上一轮我把「分层存储（episode / semantic 分开）」列成待办，理由是
「根治事实排序补丁」。真去查发现：**episodes 表已经有 56 条**，
都有证据链、都有时间、摘要确实是抽象过的（与段落正文相似度仅 0.12~0.56）。

所以「缺分层」这个说法是错的。缺的是**另一件事**。

### 17.2 真实缺口：`search` 模式根本不查 episode

`MemorySearchService.search_memory` 支持 5 种 mode：

| mode | 是否查 episode |
| --- | --- |
| `episode` | ✅ |
| `aggregate` | ✅（`_aggregate_episode`） |
| **`search`** | **❌** |

而生产用的全是 `search`：

```
heuristic_injector.py:183   → mode="search"
query_memory.py:283         → mode="search"
```

**也就是说：56 条 episode 建好了、维护着、有覆盖率——
但在真实对话里，从来没有一条进过 prompt。**

这是「建好了但没接线」的典型：所有单测都能过，因为没人测「生产用的那个 mode 会不会用上它」。

### 17.3 依据（外部资料）

**[ES-Mem, arXiv:2601.07582](https://arxiv.org/html/2601.07582v2)**
（Event Segmentation-Based Memory，事件分割记忆）

它的消融实验写得很直接：

> "w/o es exhibits **significant degradation in Multi Hop and Temporal tasks**,
> validating that dynamic segmentation preserves the semantic integrity
> required for complex reasoning."

它的 LongMemEval-S 结果对比（GPT-4o-mini backbone）：

| 方法 | Temporal | Multi-Session | Overall |
| --- | --- | --- | --- |
| MemoryOS（扁平） | 32.33 | 31.06 | 44.66 |
| Naive RAG | 39.85 | 48.48 | 60.90 |
| **ES-Mem（分层+事件）** | **64.66** | **66.17** | **72.40** |

**Temporal 从 32 提到 65，正好是我们评测里最容易失败的那一类。**

它的三层结构（§3.2）：

| Level | 内容 | 作用 |
| --- | --- | --- |
| 1 | 精炼事件边界 | 高层认知锚点 |
| 2 | 事件摘要 | 细粒度内容匹配的索引 |
| 3 | **原始上下文** | 「ground truth source」，最终喂给模型 |

消融里明确说：**"w/o raw suffers the most severe overall drop"** ——
摘要能证明「这段时间在聊这个」，但回答细节还得靠原文。

### 17.4 实现

在 `search` 分支主检索之后追加 episode 通道：
`memory_search_service._append_episode_hits()`

对应论文三层的简化版：
- 召回**事件摘要**（Level 2）
- 把该事件覆盖的**原始段落**一并带出（Level 3，最多 2 条）

三条保守原则：

1. **不改已有命中的顺序** —— episode 只往后加
2. **去重** —— 已被召回覆盖的段落不再重复带出
3. **失败即忽略** —— episode 出任何问题都只是「少几条」，不让整次检索失败

### 17.5 ★ 第一版写错了：追加的 5 条全被扔掉

第一版是「先追加、再 `filtered[:limit]` 截断」。
主检索本来就返回满 `limit` 条（10 条），追加的 5 条在截断时**全部被丢弃**。

表面看代码在跑（`_append_episode_hits` 单独调用返回 5 条、验证全绿），
但走 `search_memory` 出来的结果里 episode 贡献是 **0**。

**修法：先给 episode 留名额。**

```python
ep_budget = self._episode_budget(limit)          # limit//4，上限 3
kept_main = filtered[: max(1, limit - ep_budget)]
filtered = await self._append_episode_hits(kept_main, ...)
filtered = filtered[:limit]
```

`limit=10` → episode 占 2 个名额，主检索 8 条。

### 17.6 ★ 第二个错：episode 命中丢了时间，严评反而掉了 1 分

加完通道跑严评：**14/15 → 13/15**，`ipynb 时间题` 反而失败了。

原因：`_attach_time_meta` 只处理 `type == "paragraph"`。
episode 命中虽然有 `event_time_start/end`，但不会被渲染成 `[昨天 14:19]`。

结果是：**新通道把上下文撑大了，但时间信息丢了** → 时间题得分下降。
这和 §9（`time_meta` 从来没生效）是同一个坑的第二次出现。

修在两处（双保险）：
1. `_append_episode_hits` 在**源头**就填好 `metadata.time_meta`
2. `_attach_time_meta` 增加 `episode` 分支，把 `event_time_start/end` 翻成 `time_meta`

修完：`EP [昨天 13:30~15:53] ...` —— episode 命中带上了时间。
严评回到 **14/15**。

### 17.7 效果

`tools/_p180_verify_episode_in_search.py`，5 个查询 × 2 条断言 = **11/11**：

| 查询 | 分布 | episode 贡献 |
| --- | --- | --- |
| 10月20号凌晨大家在干什么 | 7 paragraph + 2 episode + 1 raw | 3 |
| 最近一次提到 ipynb 是什么时候 | 8 paragraph + 2 episode | 2 |
| 大肥鱼答应帮 Tutu 做什么 | 8 paragraph + 2 episode | 2 |
| 过客的壳币有多少 | 8 paragraph + 2 episode | 2 |
| 群里在玩什么游戏 | 8 paragraph + 2 episode | 2 |

命中质量示例（「大肥鱼答应帮 Tutu 做什么」）：

```
[EP] 大肥鱼答应Tutu找会飞滑板视频，指引搜索B站UP主「神奇阿宇Ayu」
     播放量297万的视频；并分享MiniMax M3.1 ...
```

**每一条都断言了「原有通道仍保留」** —— 追加不挤占。

回归：记忆评测 **30/30**，四个单测 43/43，无退化。

### 17.8 教训

**「建好了」和「接上了」是两件事。**

56 条 episode 建了、维护着、有覆盖率 60.8%，所有单测都过 ——
但生产走的那个 mode 从来不看它们。这种缺陷**没有任何报错**，
因为它不是坏了，是**没接线**。

判断方法：**顺着生产实际调用的那个入口往下走一遍**，
看每一层有没有被真正用上。而不是看「这个能力是否存在」。

## §19 （第 180 轮续）★ 事实写入链路终于真实跑通了

### 19.1 上一轮留下的悬念

第 179 轮 §16 验证过「`ingest_text` 能写库」，但**真实对话里一条新事实都没进来**。
当时的结论是「链路是通的，缺的是输入」。

本轮复查发现**它真的进来了**：

```
最近 1h 新增事实: 2 条
最新事实: 2026-10-21 14:08:36   ← 与最新段落同一秒
最新 person_fact 段落: 2026-10-21 14:08:36
```

写入的两条：

```
菜蛆想玩元神
菜蛆不想面对综合作业
```

**主语是正确的真人名**（`菜蛆`），不是代词、不是 bot。
person_id 正确，claim 状态 active。

**这是 §10「prompt 瘦身」修复在真实链路上的第一次成功验证。**
从 04:53 断流到 14:08 恢复，中间隔了 9 小时——原因就是那段长 prompt。

### 19.2 但立刻发现这些事实没有时间

健康检查报「段落无任何时间：2 段」，正是这两条刚写的事实。

**根因**：`person_info.store_person_memory_from_answer` 调 `ingest_text` 时
**一个时间参数都没传**：

```python
result = await memory_service.ingest_text(
    external_id=external_id,
    source_type="person_fact",
    text=clean_content,
    ...
    # ← 这里没有 timestamp / time_start / time_end
)
```

于是 `ingest_service` 内部 `time_meta(timestamp, time_start, time_end)`
三个值全是 None → 段落 `event_time*` 三个字段全空。

**后果**：这些事实无法按时间定位，问「这条什么时候的事」答不出来。

### 19.3 修法：用证据消息的真实时间

新增 `_resolve_evidence_timestamp(evidence_message_ids)`：

```python
# 优先：证据消息的真实时间（"这件事发生的时间"）
fact_timestamp = _resolve_evidence_timestamp(evidence_message_ids)
if fact_timestamp is None:
    fact_timestamp = datetime.now().timestamp()   # 退回写入时刻
```

**为什么不用 `now`**：事实是**隔一段时间才回写**的。一条 14:08:18 的消息，
可能要等攒够 36 条才触发摘要，14:08:36 才写成事实。
用 `now` 会让时间整体后移。

实测这条差 17 秒（14:12:28 的消息 → 14:12:45 写入），
跨度大时能差几十分钟。

**为什么取最大值**：`evidence_message_ids` 可能有几条，
取**最后一条**的时间更接近"这件事说完的时刻"。

### 19.4 回填历史

代码修了，但已有 2 条空值不会自己长出来。
`tools/_p180_backfill_fact_time.py`：

| 依据 | 优先级 | 粒度 | 置信度 |
| --- | --- | --- | --- |
| `evidence_message_ids` 里消息的真实时间 | 1（最准） | second | 1.0 |
| 段落 `created_at` | 2（兜底） | approximate | 0.4 |

回填时写 `metadata.p180_time_backfilled` 标记，日后能查「这条时间是不是后补的」。

结果：**2 条回填，仍无时间 = 0，granularity=second，confidence=1.0**。

## §20 （第 180 轮续）★ 改 episode 分割粒度：1.55 段 → 1.76 段

### 20.1 先纠正覆盖率那个误导

上轮我说「覆盖率 60.8% 是缺口」。这轮拆开看：

| 类型 | 未覆盖数 | 该不该覆盖 |
| --- | --- | --- |
| `person_fact` | **45** | **不该**（有意排除，见下） |
| `chat_summary` | 6 | 大多是「本时段无新增事实」的空摘要，也不该 |

`profile_policy.py` 里写得很清楚：

```python
disabled_source_types = ["person_fact", "knowledge_pack"]
# 已加工知识包含有权威段落、实体和关系，不应再次交给 LLM 生成 Episode。
```

**所以 60.8% 不是缺陷，是设计。** 按 `chat_summary` 口径算是 **98.8%**。

真正的问题只剩下一个：**粒度 1.55 段太细**（35/56 个只覆盖 1 段）。

### 20.2 依据

**[Nemori arXiv:2508.03341](https://arxiv.org/html/2508.03341v1)** 把粒度问题讲得最清楚：

> 现有 MAG 系统常用 Single Message / Interaction Pair 作基本单元，
> 这 "produce **fragmented memories that lack broader semantic context**"。
> 理想单元应对应**一个连贯事件**。

它的 LongMemEval_S 结果（GPT-4o-mini）：

| 类别 | Full-Context | Nemori |
| --- | --- | --- |
| **temporal-reasoning** | 42.1% | **61.7%** |
| multi-session | 38.3% | 51.1% |
| **single-session-preference** | 6.7% | **46.7%** |
| knowledge-update | 78.2% | 61.5%（**反而降**） |

temporal 和 preference 大幅提升，**knowledge-update 反而降** ——
这正好对应我们唯一失败的 `过客的壳币`（知识更新类）。

**[ES-Mem arXiv:2601.07582](https://arxiv.org/html/2601.07582v2)**：
事件是 "high internal semantic homogeneity and bounded by **distinct shifts
in topic, task phases, or interaction patterns**"。

### 20.3 第一次改：只加文字规则，失败

改了 `_build_prompt`，加了「合并判据 / 拆分判据 / 下限 2-6 段 / 不许无故丢段落」。

测 8 段 → 3 个 episode，平均 2.67 段，覆盖率 100%。**看起来成了。**

但重建真实数据（13 段）→ **11 个 episode，平均 1.18 段**，比原来还差。

### 20.4 看清真相：模型不认抽象规则，只认具体反例

把那 13 段打出来看：

```
[ 7] 《老经》在牛牛小游戏中多轮下注...余额 112
[ 8] 《老经》继续...余额 327
[ 9] 《老经》继续...余额 532
[10] 《老经》继续下注...余额 552
[11] 《老经》继续下注...额度已用满
[12] 《老经》继续下注...余额 522
[13] 《老经》的壳币余额最终变为 100
```

**这 7 段全是「《老经》玩牛牛」这一个连续事件**（余额在变，但事件没变），
模型把它拆成了 6 个 episode（`multi-round` / `continues` /
`nears daily cap` / `cap reached` / `Final rounds` …）。

我原来写的是抽象规则「同一活动多轮 → 合并」，模型执行不到位。

### 20.5 第二次改：把反例写进 prompt

v3 的 prompt 第一段就是：

```
## THE SINGLE MOST IMPORTANT RULE
**One activity = one episode, no matter how many paragraphs it spans.**

Real example of what NOT to do (this is the actual failure we are fixing):
  paragraphs 7-13 all describe the same person playing successive rounds of
  the same game, with the score changing each round.
  WRONG: 6 episodes like 'multi-round' / 'continues' / 'nears cap' / 'cap reached'
  RIGHT: 1 episode, e.g. '老经 连续玩牛牛直到当日额度用满'
A changing number is NOT a new event. A new round is NOT a new event.
```

**同样的 13 段，v3 产出 5 个 episode，平均 2.60 段，覆盖率 100%。**
那个 7 段的事件被正确合并成了 1 个。

三个来源综合：82 段 → 46 个 episode，平均 1.78 段，覆盖率 97.6%。

### 20.6 ★ 踩的坑一：改了 prompt 但重建不生效

第一次调 `rebuild_episodes_for_sources` 返回：

```json
{"rebuilt": 1, "reused_episode_count": 6, "recomputed_group_count": 0}
```

**一条都没重算。** 因为它按 `generation_signature()` 判断"能不能复用"，
而那个签名里**只有版本号和模型配置，不含 prompt 内容**。

修：`SEGMENTATION_VERSION` 从 `v2` 升到 `v3`。

**教训：改了 prompt 必须升版本号，否则重建会被判为"可复用"。**

### 20.7 ★ 踩的坑二：租约卡死，永久 `not_claimed`

升版本后仍然 `not_claimed`。查 `episode_rebuild_sources`：

```
status='running'  claimed=210  desired=213  lease_until=14:45:59（未来 26 分钟）
```

**上次重建中途被杀（我停了大肥鱼），租约没释放。**

抢锁条件里有一条最容易漏：

```sql
AND (lease_token IS NULL OR COALESCE(lease_until, 0) <= now)
```

我第一版只清了 `claimed_revision`，`lease_until` 还是未来时间 → 永远抢不到。

修：`tools/_p180_release_stuck_lease.py` 要同时清四样：

```sql
SET status='pending', claimed_revision=NULL,
    lease_token=NULL, lease_until=0, claimed_generation_hash=NULL
```

清完立刻重建成功（`recomputed_group_count: 2`）。

### 20.8 结果

| 指标 | 改造前 | 改造后 |
| --- | --- | --- |
| episode 数 | 56 | **49** |
| 平均段数 | **1.55** | **1.76** |
| 只有 1 段 | 35（62%） | **26（53%）** |
| 最大段数 | 5 | **8** |
| chat_summary 覆盖率 | ~93% | **98.8%** |

那个 **8 段** 的 episode 就是「老经玩牛牛」的完整事件 —— 事件层终于在做它该做的事。

## §21 （第 180 轮续）★ 时间标签补绝对日期

### 21.1 加完 episode 后严评反而掉分

episode 接线 + 粒度改造做完，严评 **14/15 → 13/15**。失败的是：

> `10月20号凌晨大家在干什么`
> ← 检索内容提到的是"昨天""今天"凌晨...但**无法确认对应10月20号**

### 21.2 根因：相对时间没换算成绝对日期

`_RELATIVE_DAY_TEXT` 只有 `今天/昨天/前天`：

```python
day_text = _RELATIVE_DAY_TEXT.get(start_delta) or _format_absolute(...)
```

**两天内只写「昨天」，模型不知道"今天"是哪天**，所以没法把「昨天」对应到「10-20」。

而 episode 命中内容更长、日期词更多，让这个缺陷更明显了。

### 21.3 修法：相对 + 绝对并列

新增 `_day_label()`：

```
昨天 10-20 03:13~07:04
今天 10-21 14:12
前天 10-19 14:00~15:30
10月18日 10:00~11:30     ← 超过前天的直接绝对
```

**为什么不用「昨天(10月20日)」**：时间标签出现在**每一条记忆**前面，
一天几十条时每个多 6 个字符就是几百字符的 prompt 开销。
`10-20` 紧凑且够模型理解。

### 21.4 ★ 顺带发现两道题是我自己写错的

修完日期仍失败，去看真实数据：

```
=== ipynb 相关段落的时间 ===
  2026-10-20 13:30:12  ...
  2026-10-20 14:19:40  ...
  2026-10-20 14:21:01  ...
```

**ipynb 全部在 10-20，根本不在 10-21。** 我的严评题集 `expect` 写的是
"10-21 上午，作业运行报错"——**题目写错了**。

`10月20号凌晨` 那道也一样：我写的 expect 是
"折腾记忆系统 / 催睡觉 / 抓壳 / 三点还在忙"，
但真实数据里 10-20 凌晨那段是**催睡觉 + 约饭**，
「折腾记忆系统」在 10-21。

**又是「尺子量错了」。** 已按真实数据校正两道题的 expect。

修完：**14/15**，时间题全绿。

### 21.5 教训

**评测题集里的 `expect` 也是数据，也会过时和写错。**
每次严评失败，先问「是产品错了，还是我的期望值错了」。

判断方法：**去库里查真实值**，不要凭印象。

## §22 （第 180 轮续）健康检查的两个运维坑

### 22.1 ★ 循环被「停大肥鱼」误杀

健康快照循环启动后，每次停大肥鱼它都会消失。

根因在**命令行匹配**：

```
循环:      D:\MaiBot\.venv\Scripts\python.exe ... _p179_health_loop.py
                        ^^^^^^ 含 "MaiBot"
停 bot:    CommandLine -like '*MaiBot*'      ← 命中！
```

同一个坑还有 `dfy_panel.py`（也在 MaiBot venv 下跑）。

**修法**：循环改用 **QQBot 的 venv**（命令行里就没有 "MaiBot" 了）。
它只是调 `subprocess.run`，用什么 venv 都能跑。

**教训：按命令行的模糊子串杀进程是危险的。**
停 bot 应该匹配**脚本名**（`*bot.py*` / `*-m src.runtime*`），
而不是 venv 路径。

### 22.2 ★ `pythonw` 静默退出

用 `pythonw.exe` 启动循环，进程不存在、日志没写、**没有任何错误**。

原因：`pythonw` 没有 stdout/stderr，任何输出异常都丢失。

**修法**：用 `python.exe` + `-RedirectStandardOutput/Error`。
或者接受 `pythonw` 但确保代码自身写日志文件（我们两边都做了）。

**教训：`pythonw` 启动的东西「看不见」= 「不知道它活没活」。**
凡是常驻进程，必须有一个**独立的存活证据**（pid 文件 / 心跳日志）。

### 22.3 查进程不能用 `CimInstance ... -like '*xxx*'` 判断存活

我在 `pythonw` 场景下用 `Get-CimInstance | ? CommandLine -like` 查，
结果是 0 个，于是以为"没启动"，实际它活得好好的。

后来用 `Start-Process -PassThru` 的 `HasExited` 属性才确认真实状态。

**教训：判断进程存活用 `Get-Process -Id` 或 `-PassThru` 对象，
不要靠命令行模糊匹配。**

### 22.4 死段落的「有意 vs 意外」

改完后出现 1 个死段落，健康检查报 BAD。

但如果去看它是什么：

```
hash=166333d2...
  claim = Tutu转发指出大肥鱼特别喜欢用的句式是「不是....是....」
  status = retracted
```

这条事实本身就是错的（「大肥鱼喜欢某句式」被归成了「Tutu 的偏好」），
撤回它、让检索不再返回，**正是正确行为**。

**修法**：健康检查看 `fact_transitions.reason`，
带 `p1xx_*` / `manual` / `*_fix` / `*_dedupe` 等意图标记的算「有意撤回」→ WARN；
其余算可疑 → BAD。

这样既不掩盖真事故（§11 那次 12 段误杀），也不对「清理脏数据」报假警。

## §24 （第 182 轮）★ 身份认知污染：大肥鱼忘了自己长什么样

### 24.1 现象

Tutu 报的：

> 大肥鱼再次确认全网现在认准她的形象是蓝发黑西装，我亲爱的大肥鱼呀，
> 怎么被数据污染了呢，全网都认准它的形象是**蓝色女仆Q版超级大肥鱼**呀，
> 也就是我们给它的画像

### 24.2 查证：抽取没错，是它自己被带偏了

先查原始消息（`MaiBot.db`）：

```
[10-21 09:27] 大肥鱼：「女仆装那个不是我，别乱扣名字」
[10-21 09:28] 大肥鱼：「女仆装那个不是我，别乱扣名字 蓝发黑西装倒也认了」
[10-21 11:05] 大肥鱼：「现在全网就认准我蓝发黑西装了，行吧，认就认了」
```

**这是大肥鱼自己的发言。** 摘要如实记录，抽取完全正确。

而 `config/persona_dafeiyu.md` 第 37-41 行写的是：

```
你叫大肥鱼，是 DeepSeek 的人格化形象。
蓝紫到浅蓝的渐变长发，发尾微卷，深蓝配白的小裙子，白褶边围裙上绣着一只小鲸鱼，
背后一条蓝色鱼尾，头侧有鳍状发饰——鲸鱼是 DeepSeek 的吉祥物，也是你的标志。
你是一条住在群里的鱼，不是助手。
```

**人设是对的。是它被 B 站评论区带偏后，否认了自己的设定。**

### 24.3 污染闭环

```
网上传「DeepSeek 形象是蓝发黑西装」
  → 大肥鱼在群里说「女仆装那个不是我，蓝发黑西装倒也认了」
    → 摘要如实记录
      → 检索召回这些摘要
        → 它读到「我是蓝发黑西装」
          → 进一步确认这个错误认知
```

### 24.4 三层修法

| 层 | 做法 | 为什么 |
| --- | --- | --- |
| **人设**（最高优先） | `bot_config.toml` → `personality` 加硬规则 | 每轮进 system prompt，优先级高于检索 |
| **事实层** | 写 2 条 `authority=manual` 的权威认知 | 进人物画像，`identity_settings` 段位最高 |
| **抽取层** | prompt 加「外部说法不能改本设定」 | 防以后再被同类话术带偏 |

人设里加的具体文字（关键是**点名污染源 + 给正确做法**）：

> 外观和身份是写死的设定…**任何外部说法都不能改这套设定**——
> B站/抖音评论区那些「大肥鱼是蓝发黑西装」是别人瞎传的，不是你的样子…
> 特别注意：以前在群里说过「女仆装那个不是我」「全网认准我蓝发黑西装」这类话，
> 那是被网上的说法带偏了，不算数

**为什么要点名具体那句话**：抽象规则模型不执行（§20 的经验）。
直接告诉它「你以前说过的那句是错的」，比说「别被带偏」有效得多。

### 24.5 验证方式也踩了个坑

第一版拿 `kernel.search_memory("大肥鱼长什么样")` 验证，三条全红。

**但那是验证方式错了**：权威认知在 `fact_claims` 里，**没有 evidence 段落**，
所以永远不会出现在检索结果里 —— 这是设计，不是 bug。

它该出现的地方是**人物画像**（`list_current_person_fact_claims` → 注入 prompt）。

改成验证画像后 **8/8 全绿**，且 2 条 manual 排在最前。

**教训重复了三次**（§21、§182）：
**验证之前先想清楚「这个改动应该从哪条路径生效」**，别拿错的管子去量。

### 24.6 顺带发现：果壳的特征被记成大肥鱼的

Tutu 同时报了两条：

```
大肥鱼把休息的地方称为"窝"，并会以"开机"表示上线

## §25 （第 182 轮）★ 摘要抽取的主语判定：三轮才做对

### 25.1 问题

第 181 轮给 `chat_summary` 加了规则抽取，但主语判定不对。
实测 14 条壳币 claim 里 3 条挂错人：

| 挂在谁名下 | 句子 | 数值真正属于 |
| --- | --- | --- |
| Tutu | `…果壳显示大肥鱼当前壳币为 547` | **大肥鱼** |
| 过客 | `…大肥鱼在对话中确认了自己的壳币已达到 647` | **大肥鱼** |

### 25.2 三轮迭代

**v1：全文找名字，取最靠前的** → 错。
「大肥鱼吐槽过客壳币不足」两个名字都在，主角是大肥鱼但数值属于过客。

**v2：只认句首 12 字内的名字** → 大部分对，长句仍错。
「Tutu 提醒…果壳显示大肥鱼当前壳币为 547」句首是 Tutu。

**v3：取「离数值最近的人名」** → 又有新错。
这两种句子无法用距离区分：

```
① 「过客…壳币经多轮 +30 奖励后累计至 258」     正确人名离 258 有 43 字
② 「大肥鱼…抓住过客…壳币从 547 增加到 647」    错误人名（宾语）离 647 只有 38 字
```

38 < 43，取反。

**v4（最终）：语法结构优先，句首兜底**

1. 「**人名 + 紧邻指标词**」（12 字窗口内）→ 用它，最可靠
   `过客的壳币数量为 138`、`果壳显示大肥鱼当前壳币为 547`
2. 没有这种结构 → **句首 10 字内的人名**（中文主语位）
   `过客…累计至 258` ✅、`大肥鱼…增加到 647` ✅
3. 都没有 → 空，调用方跳过

结果：**14/14 主语测试全绿，错挂从 3 条降到 2 条并正确识别**。

### 25.3 另外两个 bug

**bug 1：单字昵称抢先匹配**

34 个候选里有昵称只有一个字的。`head.rfind("客")` 命中在「过**客**的壳币」第 1 位，
比「过客」的第 0 位更靠后，把正确结果覆盖掉。

修：**名字长度 < 2 的不参与**。

**bug 2：sqlite 游标被内部查询搞乱**

脚本里 `for r in cursor` 迭代途中，`Person()` 内部用同一个连接查库，
导致 `_resolve_metric_subject` 明明能算出来、脚本里却全是空。

修：**先 `fetchall()` 再处理**。

**教训：在 sqlite 游标迭代里调任何会查库的函数，都可能静默出错。**

## §26 （第 182 轮）★ 给「最新值」打标：解决多值矛盾

### 26.1 问题

问「过客的壳币有多少」，检索返回 138 / 216 / 258 / 368 / 547 五条带日期的段落。
模型答不出：

> 壳币存在多个互相矛盾的值，无法确定哪个最新

### 26.2 为什么时间标签不够

上一轮（§21）已经让每条记忆带上 `[昨天 10-20 12:05]` 这样的时间。
但**数值大小和新鲜度无关**：

```
10-20 12:05  壳币 547
10-21 00:24  壳币 368   ← 更晚，但更小（玩五连抽花掉了）
```

所以「取最大的」会答错，「取时间最新的」才对 —— 但模型不会自己这么算。

### 26.3 依据与做法

MemStrata（arXiv:2606.26511 §4）的读侧设计：
检索不能只给一堆历史值，**必须让读者知道哪条是当前状态**。
否则读者要么弃答、要么拿旧值当答案（后者更糟）。

`memory_search_service._mark_latest_metric_hits()`：

1. 对每条命中识别 `(主语, 指标)`（复用 `_resolve_metric_subject` + `extract_metric_value`）
2. 同组内按时间取最新，在 `metadata.time_meta` 打 `metric_is_latest=True`
3. 渲染层显示 `[今天 10-21 00:24 ·最新/共7条]`

**一条都不删**，只加标记 —— 历史演变本身有价值（§16 的教训：
不能因为「可能落后」就删掉历史）。

### 26.4 但有一道题还是救不回来——因为数据本身就是矛盾的

「过客的壳币有多少」加了标记后**仍然失败**。查原因：

```
[今天 10-21 00:24~00:28] …壳币累积到 368
[今天 10-21 00:24~00:27] …壳币不足（216，差 4）未能抽成
```

**368 和 216 相差不到一分钟。** 大概是先累积后被五连抽花掉，
但记录没写清先后。换什么模型都只能猜。

这不是检索能力问题，是**数据粒度问题**。
所以把这道题换成能验证的：

```
「谁的壳币曾经到过 547」 → 过客
```

验证的是「能不能定位数值归属」，而不是「能不能消解数据自身的矛盾」。

**教训：评测题也得是「有答案」的题。**
连续两轮我都在修自己写错的期望值（§21 的 ipynb、§24 的 10-20 凌晨、这条）。

## §30 （第 183 轮）★ 评估后决定**不做**：检索端消费 `expired_at`

### 30.1 原计划

待办列表里有一项「检索端消费 `expired_at`」，
想法是让检索过滤掉已失效的事实。

### 30.2 查了外部资料

[Zep/Graphiti](https://arxiv.org/html/2501.13956v1) 的设计是：
> Outdated facts are invalidated by temporal logic —
> **preserved as history, removed from current state**.

听起来该做。但去看我们自己的代码，发现两件事：

**① 已经做了（模糊修改那条线）**

`_filter_current_effective_hits` 会按 `metadata.memory_change.valid_to`
过滤 —— 但它查的是**模糊修改计划**用的字段，不是 `fact_claims.expired_at`。

**② 不做才是对的（事实状态那条线）**

`_filter_superseded_person_fact_hits` → `list_paragraphs_with_inactive_fact_claims`
**只判 `retracted`，不判 `superseded`**。

这是有意设计 —— §11 那次把 `superseded` 当 `retracted`，
**误杀了 12 个本来正确的历史段落**。

### 30.3 结论

如果把 `superseded` 也纳入过滤：

- 好处：问「当前值」时不会看到一堆旧值
- 代价：**历史演变过程全部消失**（§16 的教训：不能因为「可能落后」就删）

而这轮的替代方案（§26 的 `metric_is_latest` 标记）已经解决了「分不清哪个最新」：

```
[今天 10-21 00:24~00:28 ·最新/共7条] …壳币累积到 368
[昨天 10-20 12:05~12:09]        …壳币累计至 547
```

**保留全部历史 + 明确标出最新**，比「删掉非最新的」信息更全。

### 30.4 教训

**有些 TODO 做完会变坏。**

待办列表是在缺信息的情况下写的。执行前要重新评估：
- 这个问题真的存在吗？
- 现有的替代方案够不够？
- 做了会不会破坏别的保证？

## §31 （第 183 轮）★★ 修了 2 个插件的「永不触发的入口」

### 31.1 问题

2. 《老经》当天净赢额度用满
3. 大肥鱼的围观反应（称赞 → 打脸 → 收回）

但它被当成「一条事实」存了下来。后果：

- 检索时**整段噪音一起返回**，模型要自己从 157 字里挑数字
- 进人物画像时占掉大量篇幅（画像每轮都注入）
- 同指标互相取代时，等于**用一个长段盖掉另一个长段**，演变过程全丢

**根因**：第 181 轮加规则抽取时，`value_text` 直接存了 `statement`（整段）。

### 33.2 修法

代码层加 `compact_metric_fact()`：按「主语 + 指标中文名 + 值」**拼短句**。

```python
compact_metric_fact("《老经》", "guoke.shell_coin", "552")
# → "《老经》的壳币数量为 552"   （14 字，原来 157 字）
```

需要一个 `_METRIC_CN_NAME` 映射表（`guoke.shell_coin` → `壳币数量` 等）。

**为什么不用 raw_text 改写**：规则改写中文叙述很不可靠
（要处理省略、语序、指代）。直接拼短句信息密度最高且绝不出错。

**压不出来就放弃这条** —— 宁可少一条事实，也不要一条读起来像段落的"事实"。
原文段落还在库里，需要上下文时照样查得到（职责分离）。

原句存进 `evidence_metadata.raw_sentence`，日后要追溯还在。

### 33.3 ★★ 迁移历史数据时踩的坑：两次验证都失效

写迁移脚本时，dry-run 抓到一条会压错的：

```
旧：「群友过客的果壳图鉴已集满62种，壳币138。
     大肥鱼在五连抽中抽到5只全新角色，图鉴增至17/62…」
新：「过客的图鉴收集进度为 17」
```

**17 是大肥鱼的图鉴，不是过客的。**

**第一次验证（失效）**：用 `_resolve_metric_subject(old, [scope])` 重判。
只传 `[scope]` 一个候选人 → **等于强制归给当前主语**，验证等于没做。

**第二次验证（还是失效）**：改成传全量候选人。还是没拦住。因为
`_resolve_metric_subject` 判的是「**整段的主语**」：
句子开头就是「过客的果壳图鉴」，于是判成过客 —— 而值是第二句的。

**第三次（正确）**：直接看**数值在原文里的位置**，取它前面最近的人名。

```python
value_at = old.find(value)
head = old[:value_at]
nearest = 最靠后的人名 in head
if nearest and nearest != scope_name:
    skip  # 值不属于当前主语
```

这才是「这个数字属于谁」。

结果：**可压缩 2 条，正确跳过 1 条**，理由精确
「数值 17 属于「大肥鱼」不是「过客」」。

### 33.4 同一个验证也加进了生产代码

迁移脚本只能修历史数据。新写入还会出同样问题。
所以 `_write_summary_metric_claims` 里也加了值位置验证：

```python
value_at = statement.find(value)
head = statement[:value_at]
# 取 head 里最靠后的人名
if nearest_name and nearest_name != my_name:
    return []   # 跳过
```

**保守取舍**：宁可少记一条，也不要记错一条 ——
错的会进人物画像、每轮都被注入，而且事后很难发现（§24 的身份污染就是这么来的）。

### 33.5 还有一个连带 bug

端到端测试 `_p181_verify_summary_facts.py` 挂了：找不到刚写入的 claim。

原因：它用 `value_text LIKE '%MARK%'` 查，而 `value_text` 现在是压缩后的短句，
测试标记（在原文末尾）**不会出现在里面**。

连带 `cleanup()` 也漏删，残留导致「没新增 claim」的假失败。

修：改成从 `fact_evidence.metadata_json.raw_sentence` 找（原句存在那里）。
跑第二次才正常（第一次清残留）。

### 33.6 结果

| 指标 | 修前 | 修后 |
| --- | --- | --- |
| 事实平均长度 | 24.6 字 | **17.5 字** |
| 超长事实(>60字) | 4 条 | **1 条**（那条主语不一致的，保留是对的） |
| 无证据 claim | 2 条 | **0 条**（判据修正） |

剩下的 1 条 86 字那条保留原样 —— 它内容不算错（过客图鉴 62/62），
只是和 17 混淆了。要拆成两条 claim 需要 LLM，留给以后。

### 33.7 一条方法论

**「宁可少记一条，也不要记错一条」。**

错的记忆会：
- 进人物画像，每轮注入
- 被检索召回，误导回答
- 事后极难发现（它看起来像一条正常事实）

而漏记的代价只是「这条没记住」，用户问起来会说「不知道」——
**这比自信地答错要好**。

## §35 （第 185 轮）★ 量化检索噪音，抓到 episode 通道的零分污染

### 35.1 为什么先量化

目标里有「噪音控制」，但前几轮只做定性判断（「超长事实是噪音」）。
**没人量化过：检索一次返回 10 条，里面到底几条有用？**

写了 `_p185_search_noise.py`：10 个互不相关的查询 × top-10，
统计 score 分布、低分占比、以及「同一个段落被多少个不同查询召回」。

### 35.2 ★ 第一个发现：score 跨通道不可比

第一版把所有权中的 score 混在一起算平均，得出「平均 2.431」。
**这个数字毫无意义** —— 按通道拆开才发现：

| 通道 | 量纲 | 实测范围 |
| --- | --- | --- |
| `paragraph/dual_vector_pool` | 余弦相似度 | 0.27 ~ 0.66 |
| `episode/episode` | 加权词法分 | 0 ~ 24.5 |
| `paragraph/episode_raw` | 加权词法分 | 0 ~ 20 |

**差了 30 倍。** 混算平均等于把两种货币加在一起。

修：按 `(type, source)` 分组统计，各自的分数各自看。
阈值断言也只对段落通道做（只有它是余弦相似度）。

### 35.3 ★★ 第二个发现：episode 通道有零分命中

按通道统计后立刻看到一个刺眼的数据：

```
episode/episode   n=15  avg=10.000  min=0.000  <0.3=4
```

**4 条 score=0.000 的 episode 命中。** 它们凭什么被返回？

查具体内容 —— 问「谁的口头禅是正经点」，返回的是：

```
[EP] 0.0  元神指代澄清与像素图出处
[EP] 0.0  B站桌宠教程讨论与闲聊调侃
[EP] 0.0  老经玩牛牛
```

**和"口头禅"毫无关系。**

### 35.4 根因：融合分算完就删了

`episode_retrieval_service._fuse_branches`：

```python
bucket[episode_id]["_fusion_score"] += weight / (RRF_K + rank)
...
for item in out:
    item.pop("_fusion_score", None)   # ← 分数在这里丢了
```

而下游 `memory_search_service._append_episode_hits`：

```python
score = float(row.get("lexical_score", 0.0) or 0.0)
```

融合后的 row **既没有 `lexical_score`**（那是 lexical 分支 SQL 算的，
向量分支产的 row 没这个字段），**也没有 `_fusion_score`**（被 pop 了）
→ **score 恒为 0.0**。

后果：所有 episode 命中看起来都是 0 分，**下游想过滤都无从下手**。

**修**：融合分改名保留（`fusion_score`，不 pop），下游按来源分层取。

### 35.5 第三个发现：向量投影在凑数

修好分数传递后，噪音还在。继续查 —— 把两条分支拆开看：

```
问「谁的口头禅是正经点」：
  lexical 分支        → 0 条（正确，没有 episode 含"口头禅"）
  paragraph_evidence  → 6 条，全 0.016 量级，内容全无关
```

`paragraph_evidence` 的做法是：**段落向量检索 top-20 → 把每个段落所属的
episode 全拉进来**。

问题在「top-20」：段落检索排名靠后的本来就掺着不相关结果
（「群聊讨论」这类普适性强的段落最容易混进去），它们的 episode 自然无关。

而且 RRF 分是 `1/(60+rank)`，同分支内全是 0.015~0.017，**零区分度**。

### 35.6 修法：只用头部段落 + 相对分数阈值

实测「谁的口头禅是正经点」的向量检索前 10 名：

```
#1  0.5406  「Tutu把正经点当作口头禅」   ← 真相关
#2  0.2875                              ← 勉强沾边
...
#10 0.2577
```

**只有 #1 是真相关的。** 所以：

1. `HEAD_RANK_LIMIT = 5` —— 只用前 5 名段落做投影
2. `RELATIVE_CUTOFF = 0.6` —— 还要求 `score >= max_score * 0.6`

用**相对阈值**而不是固定 0.5：不同查询的分数分布差别很大，
固定值会让某些查询一条都剩不下。`max * 0.6` 的意思是
「和最佳命中差太远的，不算证据」。

对这条查询：max=0.5406 → 阈值 0.324 → 只留 #1。噪音全清。

## §38 （第 186 轮）★★ 找到记忆漏记的真正原因：摘要游标失效

### 38.1 怎么发现的

这轮换了个角度：不看「记忆里有什么」，看「**记忆里缺什么**」。

按小时对比消息数和段落数：

| 小时 | 消息数 | 段落数 |
| --- | --- | --- |
| 10-20 17 | 39 | **0** |
| 10-20 18 | 31 | **0** |
| 10-20 23 | 63 | **0** |
| 10-21 06 | 18 | **0** |
| 10-21 12 | 17 | **0** |

这些时段有真人对话（「大肥鱼！在在在」「好多功能可以加的」），
但**一个段落都没产生**。

### 38.2 第一层：检查点全是 0

查 `chat_summary_checkpoints` 表：

```
chat=54b58ea9ca121b0b  count=0
chat=c853337955919c46  count=0
chat=67566ee7fa036a9d  count=0
...
```

**10 条记录，`trigger_message_count` 全是 0。**

### 38.3 第二层：检查点只在「空摘要」时记录

`summary_importer` 里，`record_summary_checkpoint()` **只在一个地方被调用**：

```python
if not summary_text:
    ...
    self.metadata_store.record_summary_checkpoint(...)   # 只有这里
    return SummaryImportResult(..., skipped=True)
# 真正写了段落的正常路径 → 从来不记
```

所以检查点表里只有"没内容"的那些，而且计数还是从 metadata 取的（也是 0）。

### 38.4 第三层：段落 metadata 也只有 24/83 带游标

`_load_last_trigger_message_count()` 靠段落的 `metadata.trigger_message_count`
恢复游标。实测：

```
83 个 chat_summary 段落，只有 24 个带 trigger_message_count
```

其余 59 个的 `trigger` 是 **`image_description_ready`**（图片描述就绪触发）——
那条路径调 `ingest_summary` 时**没传** `trigger_message_count`。

### 38.5 完整因果链

```
图片描述触发的摘要 → 不带 trigger_message_count
  → 重启后 _load_last_trigger_message_count 退化成 return total
    → 游标被设成"重启那一刻的消息总数"
      → 重启前那批还没被摘要的消息被永久跳过
```

**那天重启了 6~7 次**（每次改代码都要重启），每次都可能跳过一批。
这就是 10-20 17:00/18:00/23:00 有消息但零段落的原因。

### 38.6 三处修复

**① 写段落时补齐游标**（`summary_importer`）

在写段落的**唯一出口**补：调用方没传就用窗口内消息数兜底。

```python
if not int(metadata.get("trigger_message_count") or 0):
    metadata["trigger_message_count"] = max(1, len(messages)) + 1
```

**② 有内容时也记录检查点**（`summary_importer`）

原来只在"空摘要"分支记。现在正常路径也记，两边互相兜底。

**③ 缺游标时用时间推算**（`memory_flow_service`）

老代码：

```python
if trigger > 0:
    return min(total, max(trigger, checkpoint))
return total          # ← 把游标设成"现在"，丢消息
```

新代码：用段落的 `event_time_end` 推算 ——

```python
derived = count_messages(session_id=session_id, end_time=event_time_end)
if derived > 0:
    return min(total, max(derived, checkpoint))
```

`event_time_end` 是"这次摘要覆盖到最后一条消息的时间"，
`count_messages(end_time=它)` 就是"截至那条消息的总数"——**正是游标该有的值**。

实测验算：最近 25 条段落里 20 条缺游标，**20/20 全部能按时间推算出来**，
而且数值单调递增（10-18 → 216、10-19 → 432、10-20 → 749、10-21 → 3017），
和时间对得上。

### 38.7 加了个监控指标

漏洞修了，但**老段落不会自己长出字段**。所以加了个健康检查项：

```
[v] 摘要游标完整性   最近 20 条摘要里 15 条缺 trigger_message_count（75%）
```

判据：最近 N 条摘要里缺失比例 <= 50% 算健康。

**为什么要盯它**：这个数字现在高是因为老数据占多数，
会随新数据写入**自然下降**。如果它不降反升，说明代码回归了。

### 38.8 一个反直觉的判断

「宁可重复写一条相近摘要，也不要丢消息。」

老代码 `return total` 的意图是"避免重启后立刻重复摘要"。
但代价是**永久失忆**。

从"记忆越来越好"的角度：
- 重复摘要 → 多条内容相近的段落（浪费 token、检索噪音）→ 可治
- 丢消息 → 那段时间永远不存在 → **不可逆**

所以选择用时间推算游标——它既避免"从头发一遍"，也不跳过中间的消息。

## §43 （第 188 轮）★★ 偏好类事实从来没进过人物画像

### 43.1 怎么发现的

这轮做深度体检，看「事实覆盖率」按来源拆开：

```
person_fact     51 段,  50 有事实 (98%)
chat_summary    92 段,  23 有事实 (25%)   ← 缺口
```

`chat_summary` 只有 25%。继续挖：69 个无事实的段落里**有什么类型的内容**？

| 类型 | 数量 | 占比 |
| --- | --- | --- |
| **偏好/态度** | **22** | **32%** |
| 身份/关系 | 24 | 35% |
| 纯叙述/闲聊 | 18 | 26% |
| 决定/约定 | 4 | 6% |

**22 段含明确的偏好/态度，一条都没抽出来。** 最典型的一条：

```
「大肥鱼确认自己的主食是白米饭（大白饭），不喜欢花里胡哨的搭配，
  吃白米饭才觉得踏实。」
```

**这是核心人设。** 查 `fact_claims` 里 `profile_section='interaction_preferences'`
的记录 —— **在此之前是 0 条**。

### 43.2 根因

`_write_summary_metric_claims` 只处理 `cardinality='single'`：

```python
if not metric_key or cardinality != "single":
    return []      # ← pref.like 是 'set'，全被扔掉
```

而 `pref.like` / `pref.habit` / `relation.social` 全是 `set`。
所以 `chat_summary` 这条路**一条偏好都没抽过**。

`person_fact` 那条（LLM 抽）能抽到，但它只覆盖 `person_fact` 类型的段落。

### 43.3 依据：VARS 的双轨原则

[VARS (arXiv:2603.20939)](https://arxiv.org/abs/2603.20939) 的核心设计：
用户偏好要分成**长期稳定**与**会话内瞬时**两套
（"separates stable cross-session preferences from transient within-session state"），
混在一起会让临时情绪被当成永久人设。

这条原则直接决定了实现：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 稳定偏好 | 「主食是白米饭」 | ✅ 写入事实层 |
| 瞬时状态 | 「今天不想说话」 | ❌ 不写 |

### 43.4 实现：新增 `_write_qualitative_claim`

`chat_summary` 分支现在先判 cardinality：

- `single` → 原来的定量路径（`_write_metric_claim`）
- `set` → 新的定性路径（`_write_qualitative_claim`）

定性路径的过滤（宁漏勿错）：

| 判据 | 理由 |
| --- | --- |
| 截取到第一个句号/分号 | 摘要段落长，偏好通常只在第一句 |
| 含瞬时标记（今天/刚才/这局…） | VARS 双轨原则 |
| 没有稳定词（喜欢/讨厌/习惯/主食…） | 防叙述被当成偏好 |
| 稳定词落在人名区间内 | 防「果壳**爱玩**猫」被当成"爱玩" |
| 主语不在句首 | 防「群里…凌霄…」被判成凌霄 |

### 43.5 ★★ 三个坑，每个都让结果全为空

**坑 1：`profile_section` 写错名字**

第一版写 `profile_section="preferences"`。查代码发现合法值只有三个：

```
identity_settings / stable_facts / interaction_preferences
```

写别的会**落到 `stable_facts` 桶**（那里有 fallback），
偏好就和"壳币972"混在一起，人物画像分不出"人设"和"喜好"。

**坑 2：复用错了主语判定函数**

第一版用 `_resolve_metric_subject`。但它内部第一步是
`extract_metric_value(statement)` —— **句子里没数字就返回 None**，
于是整个函数提前返回空串。

而偏好句**本来就没有数字**：
```
「大肥鱼确认自己的主食是白米饭…」→ 被判"主语空" → 丢弃
```

新增独立函数 `_resolve_sentence_subject`（只找句首人名）。

**坑 3：`len(text) > 80` 一刀切**

第一版按整段长度拒绝。实测 **65/92（71%）因为超长被拒** ——
摘要段落本来就长。

改成「截取到第一个句号再判长度」。同一句话：

```
改前：「大肥鱼确认自己的主食是白米饭…（后面 200 字无关叙述）」→ 超长拒绝
改后：只取「大肥鱼确认自己的主食是白米饭（大白饭），不喜欢花里胡哨的搭配」
```

### 43.6 ★ 一个必须收紧的误判

放松长度后立刻出现误判：

```
「群里以调侃打趣为主，凌霄与大肥鱼互相斗嘴；果壳爱玩猫称自己恢复了味觉…」
  ↑ 开头是"群里"，但"凌霄"在第 10 字 → 判成凌霄
  ↑ "爱玩"命中的其实是人名「果壳爱玩猫」的一部分
```

**会拼出「凌霄爱吃…」这种完全错的事实。**

两处收紧：

1. **去掉叙述性前缀**（群里/群内/大家/目前/随后…）后，人名必须在最前 8 字
2. **算所有人名的字符区间**，稳定词命中位置落在人名里就跳过

收紧后：误判样例被排除，可抽取的从 3 条降到 **2 条**（都是真的）。

**这个取舍是对的**：漏掉的代价是"这条没记住"，
写错的代价是"人物画像里多一条错误人设"，后者很难发现（§24 的教训）。

### 43.7 结果

回填历史数据：**写入 2 条，跳过 90 条**。

```
interaction_preferences: 0 → 2

· 大肥鱼确认自己喜欢做的事就是催群友早点睡觉
· 大肥鱼确认自己的主食是白米饭（大白饭），不喜欢花里胡哨的搭配，吃白米饭才觉得踏实。
```

两条都进了大肥鱼的人物画像，桶名正确：

```
[identity_settings       ] 大肥鱼是 DeepSeek 的人格化形象：蓝紫到浅蓝的渐变长发…
[identity_settings       ] 大肥鱼是一条住在群里的鱼…不是助手。
[interaction_preferences ] 大肥鱼确认自己喜欢做的事就是催群友早点睡觉
[interaction_preferences ] 大肥鱼确认自己的主食是白米饭…
[stable_facts            ] 大肥鱼的壳币数量为972
...
```

### 43.8 顺带修了监控判据

加完定性抽取后，健康检查立刻报「同人同指标多 active 1 组」：

```

```

**这是误报** —— `set` 类事实本来就允许多值共存，
一个人可以同时"喜欢吃辣条"和"讨厌香菜"，这是两条独立事实。

健康检查和盘点工具都加上 `COALESCE(cardinality,'single')='single'` 过滤。

## §46 （第 189 轮）★ 承诺/约定类事实：有生命周期，不能像偏好那样永久有效

### 46.1 缺口

上轮补了偏好类事实（`pref.like`）。继续挖剩下的 67 个无事实段落：

```
含「答应/承诺/约定」的段落: 5 段
fact_claims 里的承诺类事实: 0 条
```

问「大肥鱼答应过什么」只能靠段落检索撞运气。

### 46.2 依据：MS-TOD 的 confirmation state

[MS-TOD (arXiv:2505.20231)](https://arxiv.org/abs/2505.20231) 的做法：
跨会话任务要用 **`confirmation state`** 追踪 —— 每条记录带
`slot_values` 和 `confirmation_utterance_id`，**任务完成时状态会变**。

这条决定了实现和偏好抽取**不一样**：

| 维度 | 偏好 | 承诺 |
| --- | --- | --- |
| 有效期 | 永久 | **做完就过期** |
| fact_key | `pref.like`（复用） | 带日期 + 内容指纹 |
| 状态 | 永远 active | 需要能被"已完成"取代 |

### 46.3 实现要点

`fact_key = commitment:{person}:{YYYY-MM-DD}:{content_fp}`

**为什么要内容指纹**：第一版只用「人 + 日期」，实测立刻出问题 ——

```
Tutu 在 2026-10-18 有两条不同承诺：
  「与大肥鱼约定进行果壳 24 点比试」
  「与大肥鱼再次约定玩果壳 24 点游戏」
共用一个 fact_key → 被判成"同指标多 active"（矛盾）
```

但它们**本来就是两件不同的约定**。加内容指纹后：
- 同一天同一句话 → 同一个 key → 幂等
- 同一天不同约定 → 不同 key → 正常并存
- 跨天同句话 → 不同 key → 保留（能看出"又约了一次"）

`evidence_metadata` 里留了 `commitment_status="pending"` 字段位，
将来做「承诺已完成」识别时直接往上写。

### 46.4 三个过滤（都是实测踩出来的）

**① 特意不含「打算/计划/准备」**

那是意图不是承诺。实测误判：
```
「哈机密果壳正在做 ipynb 作业…大肥鱼建议其减小参数扫描组数」
```
含"建议"和别人的"打算"，会被误当成承诺。

**② 承诺词必须在分号之前**

```
「大肥鱼确认自己喜欢做的事…；群友"我是空气"承诺请大肥鱼吃大米饭」
  ↑ 承诺词在分号后，主语已经换成别人了
```

**③ 截到分号（不是只截句号）+ 长度上限 70 字**

实测这条 113 字：
```
「大肥鱼答应给 Tutu 找会飞滑板的视频…；Tutu 想让大肥鱼收藏一张
  表情包并转发到群里，大肥鱼因为工具限制做不到…」
```
分号后面换了话题（表情包），不该算同一件事。
截到分号 → **113 字变成 61 字**。

### 46.5 dry-run 也要走真实判定

第一版 dry-run 只打印 `_looks_like_commitment` 通过的 5 条，
但其中 **2 条会被内部拒掉**（承诺词在分号后 / 承诺词贴末尾）。

**dry-run 展示的必须是真正会写入的**，否则看不到真实效果。
改成 dry-run 也跑完整判定链（不碰数据库）。

结果：5 条候选 → **3 条真承诺写入，2 条噪声正确拒绝**。

[0.502] …并确认全网现在认准她的形象是蓝发黑西装…               ← 旧说法
```

**正确内容明明是第 1 名。** 问题不是排序错，是**没告诉模型"后面那些是旧的"**。

### 47.2 为什么不删那些段落

它们是**真实发生过的对话**（她当时确实跟着 B 站评论区认了）。
删掉会丢历史（§16 的教训）。而且"它曾经这么说过、后来纠正了"
本身是有价值的信息。

### 47.3 做法：规则表 + 检索时打标

新建 `core/utils/stale_claims.py`：

```python
STALE_RULES = [{
    "topic": "形象设定",
    "match": (
        "认准她的形象是蓝发黑西装",
        "认准她的 DeepSeek 形象是蓝发黑西装",
        ...
    ),
    "note": "大肥鱼的形象以人设为准：蓝紫到浅蓝渐变长发…",
}]
```

**`match` 必须写得够具体**：不能只写 `"西装"`，因为正确段落里
也可能提到"不是黑西装"（否认句）。实测 5/5 判定正确，
正确内容和否认句都没被误标。

在 `_mark_stale_claims` 里打 metadata，渲染层显示
`[今天 10-21 09:28 ⛔已被推翻,不要采信]`。

**为什么在检索出口现算而不是入库打标**：这些段落是机制之前入库的，
入库打标只能覆盖新数据，出口现算能覆盖全部（一次字符串包含检查，成本可忽略）。

### 47.4 ★★ 标记写了但没进 prompt：尺子又对不上

第一版加了标记，严评**仍然失败**。查原因：

给 `MemorySearchResult.to_text()` 加了前缀，但**严评脚本是手写拼接的**：

```python
label = format_memory_time_label(...)
parts.append(f"[{label}] {txt}")    # ← 完全不看 metadata.stale_topic
```

**这正是第 179 轮记过的教训**：「严评必须走与生产同一条渲染路径」。

修：严评补上同样的标记逻辑。

### 47.5 ★★ 更深一层：期望值本身是旧的

标记修好后，模型改口说「既有被推翻的旧设定…又有未标注推翻的新设定，
且**新内容与参考要点不一致**」。

去看 `expect`：

```python

```

但评测题没跟着改。

**教训：改了产品结论必须同步改评测期望值**，否则评测会一直判产品错。
这已经是第四次在评测题上栽（§21/§26/§39/§47）。

## §51 （第 191 轮）★ 原子事实：承诺句 61 字 → 20 字

### 51.1 上一轮留下的弱点

`_p190_retrieval_recall.py` 测出「大肥鱼答应过什么」排第 9 位。
原因是承诺句太长（61 字），里面全是执行细节：

```
「大肥鱼答应给 Tutu 找会飞滑板的视频，指定在 B 站搜索 UP 主
  「神奇阿宇Ayu」的滑板视频，称播放量约 297 万」
  ↑ 前 20 字是核心，后面 41 字是"怎么找"，检索用不上
```

### 51.2 依据：AtomMem 的原子事实

[AtomMem (arXiv:2606.19847)](https://arxiv.org/html/2606.19847v1) 的消融实验：

| 方法 | Multi-Hop F1 | Token 消耗 |
| --- | --- | --- |
| LoCoMo（原始对话） | 20.97 | 827k |
| **AtomMem-FLAT（只用原子事实）** | **37.03（+76.6%）** | **722k（最低）** |
| AtomMem（完整） | 42.50 | 21357k |

论文原话：

> **memory storage quality is paramount.** Sophisticated system
> orchestration cannot compensate for flawed memory representations
> or information loss.

它还强调原子事实必须 **self-contained**（代词消解、时间锚定）。

### 51.3 具体做法：取第一个逗号前

实测三条承诺的结构一模一样 —— **第一个逗号前就是核心**：

```
「大肥鱼答应给 Tutu 找会飞滑板的视频，指定在 B 站搜索…」
  ↑ 20 字，核心

「Tutu 与大肥鱼再次约定玩果壳 24 点游戏，Tutu 让大肥鱼开局；…」
  ↑ 23 字，核心
```

实现：`cut = text.find("，")`，要求 `12 <= cut`（否则说明逗号太早，
如「首先，…」，保留原句）。

**为什么不做得更"聪明"**：判断哪个从句是核心需要语义理解。
规则只能靠位置，而位置规则在这批数据上 3/3 都对。
接受简单方案的局限。

### 51.4 结果

| 承诺 | 修前 | 修后 |
| --- | --- | --- |
| 大肥鱼答应找滑板视频 | 61 字 | **20 字** |
| Tutu 约定玩 24 点 | 60 字 | **23 字** |
| Tutu 约定比试 | 35 字 | **22 字** |

超长事实（>60字）：**2 条 → 1 条**。

## §52 （第 191 轮）★★ 试了「episode 插队」，实测是负优化，回滚

### 52.1 想解决什么

压缩完承诺句，又跑了一次召回 ——「答应过什么」**还是排第 9**。

查排名构成：

```
1~8. 段落通道（score 0.46~0.55），全是"大肥鱼喜欢…"类内容
9.   episode（score 15.5）★ 这条才是答案
```

根因是 `return list(hits) + appended` —— **episode 无条件追加在最后**。
而承诺恰好是 episode 形式（一次对话里答应了什么）。

### 52.2 试的方案

把「分数 >= 3.0 的 episode」提到前面。

### 52.3 结果：净负优化

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| recall@1 | **83%** | **58%** ↓ 25 个点 |
| recall@5 | 92% | 100% ↑ 8 个点 |
| recall@10 | 100% | 100% |

「答应过什么」确实从第 9 位升到第 1 位，**但另外 3 条从第 1 位掉到第 3 位**
—— episode 插到前面把正确答案往后挤了。

**25 个点换 8 个点，回滚。**

### 52.4 为什么混排不行

```
段落通道 = 余弦相似度（0~1），最高分通常 0.5~0.6
episode 通道 = 加权词法分（0~24.5），最高分通常 15~22
```

只要按绝对分数混排，episode 必然全排前面 —— **但那不代表它更相关**。

这两个数字**量纲不同、不可比较**。第 185 轮量化噪音时也踩过同一个坑
（当时算出「平均 score 2.431」这个毫无意义的数字）。

### 52.5 正确的做法（还没做）

要给 episode 一个**可比较的分数**，需要先做校准：
用历史数据拟合「词法分 → 等效余弦」的映射。

这需要标注数据，不是一两行代码能做的。

**在那之前，保持原顺序是更稳的选择**：recall@10 是 100%，
答案**一定在结果里**，只是可能排后面。

代码里写了注释，避免下次又试一遍。

## §54 （第 192 轮）★★ 「时间上限」只对一条路径生效，另一条悄悄漏了

### 54.1 怎么发现的

这轮查「时间推理能力」（目标四项之一），之前只做过日期标签渲染，没量化过。

先查时间元数据完整度 —— 一开始以为有问题：

metadata JSON 里 time_granularity: 141 条全缺
```

**但查错了位置**：那两个字段是**独立的表列**，不在 JSON 里。列里数据完整：

```
time_granularity: minute 138 条, second 3 条
time_confidence:  0.95 136 条, 1.0 4 条
```

然后查**区间跨度**，发现了真问题：

| 跨度 | 条数 |
| --- | --- |
| 中位 | 40.5 分钟 |
| **> 2 小时** | **23 条（23%）** |
| **> 12 小时** | **2 条** |
| 最长 | **18.6 小时** |

而第 178 轮明明加了 `chat_summary_writeback_max_window_hours = 2.0`。

### 54.2 三层排查

**第一层**：配置对不对？—— 对，`2.0`，`_max_window_hours()` 也返回 2.0。

**第二层**：上游传了没？—— 主路径传了 `window_time_start`。

**第三层**：看那 23 条的 metadata —— **全部没有 `window_time_start` 字段**。

### 54.3 根因：图片描述补偿路径漏传

```
created=2026-10-21 13:40:33  span=3.3h  trigger=image_description_ready
created=2026-10-21 11:47:21  span=6.9h  trigger=image_description_ready
writeback_source = image_description_compensation
→ 没有 window_time_start
```

`memory_flow_service._process_description_compensations()` 是**第二条写摘要的路径**，
它用 `context_length=36` 条消息，但没传时间窗
→ `summary_importer` 里 `query_time_start=0.0` → 按条数取，
36 条稀疏消息能横跨一整天。

### 54.4 ★ 同一个位置漏了两次

| 轮次 | 漏的东西 |
| --- | --- |
| 第 187 轮 | `trigger_message_count`（摘要游标） |
| **第 192 轮** | `window_time_start` / `window_max_hours`（时间窗） |

**都是在这条 `image_description_compensation` 路径上。**

教训：**一个功能有多条写入口时，新参数要每条都补。**
否则就是「主路径对了，边路悄悄失效」——而且**不会有任何报错**。

### 54.5 修复后的决定性证据

按「有没有 `window_time_start`」分组统计全库：

| 分组 | 条数 | 中位跨度 | 最长 | **>2h** |
| --- | --- | --- | --- | --- |

| 无（历史/其它路径） | 91 | 0.65h | 18.6h | **23 条** |

**参数生效的 0 条超限，没生效的 23 条全超限。** 因果关系清楚。

## §56 （第 193 轮）★ 「不记什么」比「记什么」更需要写清楚

### 56.1 问题

查最近 24h 写入的 17 条事实，发现 **5 条是低价值噪音**：

| 事实 | 问题 |
| --- | --- |
| `菜蛆说"喝一碗"` | 一次性的口头语 |
| `菜蛆收到了别人送的两个快到期的码` | 临时状态 |
| `菜蛆之前在tap换过两次鱼干皮` | 一次性行为 |
| `Tutu支持大肥鱼` | 太模糊，没有信息量 |

老 prompt 只有一句笼统的「闲聊、寒暄、纯情绪…都不要记」——
模型仍会把"说了一句话"当成事实。

### 56.2 依据

[Schema-Grounded Memory (arXiv:2604.27906)](https://arxiv.org/html/2604.27906v2)：

> Schemas define **what must be remembered, what may be ignored, and
> which values must never be inferred** — turning relevance from an
> implicit, read-time heuristic into an **explicit, enforceable contract**.

还有一句最关键的：

> For memory, **storing incorrect facts is often worse than storing none**,
> because incorrect records become confident, reusable inputs.

判据来自一条实践的过滤器：

> "Is this information **stable, useful, and reusable**
>  beyond a single conversation?"

### 56.3 做法：六类明确排除

原来的「该记什么」太抽象，改成**具体类目 + 真实反例**：

```
【该记什么】问一句：这条三个月后还有用吗？

【★ 明确不记这六类 —— 每类都写错过】
1. 一次性说的话：「说"喝一碗"」「回了句好的」
2. 临时状态：「收到快到期的码」「今天有点累」
3. 一次性行为：「换过两次鱼干皮」「刚才点了个外卖」
4. 太模糊：「支持某人」「觉得还行」
5. 别人对 TA 的评价（除非本人明确接受）
6. 闲聊、寒暄、纯情绪、只关于 bot 的内容
```

**为什么用真实反例**：§20 的经验——模型不认抽象规则，只认具体反例。

### 56.4 结果

用那 4 条真实噪音 + 4 条有效事实测（各跑 2 次）：

| 用例 | 期望 | 结果 |
| --- | --- | --- |
| 一次性说的话 | 不记 | ✅ 2/2 |
| 临时状态 | 不记 | ✅ 2/2 |
| 一次性行为 | 不记 | ✅ 2/2 |
| 太模糊 | 不记 | ✅ 2/2 |
| 偏好（喜欢玩原神） | 记 | ✅ 2/2 |
| 口头禅（正经点） | 记 | ✅ 2/2 |
| 数值（壳币 368） | 记 | ✅ 2/2 |
| 习惯（不喜欢虐猫表情包） | 记 | ✅ 2/2 |

**8/8 全对** —— 噪音全拦下，有效事实全记住。

### 56.5 顺带控制长度

prompt 从 790 字涨到 1077 字，**超过安全线**（§10 的教训：太长会压死抽取率）。

同步压缩「该记什么」那段（去掉冗余表述），压到 **1010 字**，重测仍然 8/8。

**这个数字要盯住**：超过 1100 字就该警惕，超过 1200 字会明显压死抽取率
（第 178 轮实测：长 prompt 1/5 vs 短 prompt 3/5）。
