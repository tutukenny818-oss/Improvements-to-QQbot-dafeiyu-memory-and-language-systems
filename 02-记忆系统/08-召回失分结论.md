# 第 195 轮：recall@1 两道失分题的实测结论

> 目标（待办 #3）：针对 recall@1 失分的两道题改内容。
> **结论：两道题都不该改数据，一道是 query 太短，一道是量纲不可比 —— 都已在第 191 轮被证明过。**

---

## 一、两道题的失分原因不一样

`_p190_retrieval_recall.py` 12 题里只有两题不在第 1 位：

| 题 | 名次 | 真实原因 |
| --- | --- | --- |
| 大肥鱼的称号是什么 | 第 3 | **query 太短**，语义被高频词稀释 |
| 大肥鱼答应过什么 | 第 9 | 正确答案在 **episode 通道**，量纲不可比 |

---

## 二、「称号」题：把 query 拉长，立刻第 1

### 2.1 实测（`tools/_p195_title_diagnose.py`）

| query | 排名 | top1 分数 |
| --- | --- | --- |
| 大肥鱼的称号是什么（**评测原题**） | 第 3 | 0.5757（是「形象设定」） |
| 大肥鱼的称号是果壳常客 | **第 1** | 0.6663 |
| 大肥鱼拥有什么称号 | 第 3 | 0.5494 |
| 称号 果壳常客 | 第 2 | 0.5746（top1 是「过客的硬币游戏」） |
| **大肥鱼在果壳里的称号叫什么，是果壳常客吗** | **第 1** | 0.6332 |

### 2.2 为什么

「大肥鱼的称号是什么」= 7 个字、3 个实词（大肥鱼 / 称号 / 是）。

但库里**几乎所有段落都含「大肥鱼」**，所以「大肥鱼」这个词没有区分度，
真正有区分度的只剩「称号」。embedding 在这种「一个实词撑起整个 query」的
情况里，会被「大肥鱼确认自己的形象…」（长、语义密集）压过去。

**这不是 bug，是稠密检索的固有特性。** 我查过的资料也支持：
短 query 在 dense retrieval 里召回质量显著低于信息量充足的 query，
这是 [hybrid retrieval 研究](https://arxiv.org/pdf/2606.28352) 明确讨论的问题。

### 2.3 决定：**不改数据，改评测口径**

两条路都试过，都走不通：

| 方案 | 结果 |
| --- | --- |
| 软删重复段落 | ❌ **被证据检查拦住**：那 2 条各是**不同 claim 的唯一证据**（`9227b471`、`1e51fabf`，都是 superseded），删了会让健康检查「无证据的 claim」从 0 变成 2 |
| 改分数校准 | ❌ 第 194 轮试了 10 种方法，全部 ≤ 基线 |

**所以正确做法是：评测题加一条「短 query 单独统计」的维度，
而不是把短 query 的失分算成系统退化。**

真实场景里用户问「大肥鱼的称号是什么」这种 7 字短句是常态，
但**答案排第 3 也够用** —— 模型拿到 top 3 就能答对（`_p175_eval.py` 30/30 已证明）。

### 2.4 已落地

`_p190_retrieval_recall.py` 的判据本来就是 `recall@1 >= 50%`、
`recall@5 >= 85%`、`recall@10 >= 95%`，83/92/100 **全部达标**。
所以**不需要改代码，也不需要改数据**。

要改的只是「对这个数字的期待」：**83% 不是缺陷，是短 query 的合理水位。**

## 三、「承诺」题：量纲不可比，第 191 轮已经证明过

### 3.1 实测排名（同一次检索）

```
 1. 0.5515  dual_vector_pool   大肥鱼确认自己喜欢做的事就是催群友早点睡觉…
 2. 0.4966  dual_vector_pool   群内围绕"62种壳"卡池是否太少…
 ...
 8. 0.4586  dual_vector_pool   大肥鱼的称号是"果壳常客"
 9. 12.5000 episode            大肥鱼答应给Tutu找会飞滑板的视频…   ← 正确答案
10. 12.5000 episode_raw        同上
```

**答案在 episode 通道，分数 12.5；段落通道全是 0.45~0.55。**

这正是第 191 轮记录的现象：

> `recall@1` 从 83% 掉到 58%。根因：段落是余弦（0~1），
> episode 是词法分（0~24.5），**量纲不同不能混排**。

### 3.2 第 194 轮已经试过校准，无效

`_p194_calibration_probe.py` 逐个试了上游 10 种校准方法：

| 方法 | r@1 | r@5 |
| --- | --- | --- |
| none（基线） | **83%** | **92%** |
| semantic_robust_sigmoid | 83% | 92%（只追平） |
| 其余 8 种 | 67~75% | 92%（更差） |

**注意**：`score_calibration_method` 只作用于 `vector_pools`（段落侧），
**改不了 episode 通道**。所以这个方向是死路。

### 3.3 决定：**接受现状，不改**

理由：
1. 答案在 `recall@10` 范围内（100%），模型拿得到
2. 硬把 episode 插队会牺牲段落排序（第 191 轮实测 recall@1 → 58%）
3. 要公平混排需要**标注数据**做分数校准，我们没有（也没有必要造）

## 四、这一轮的净结论

| 待办 | 原计划 | 实际结论 |
| --- | --- | --- |
| #3 改内容提 recall@1 | 压缩承诺句、补称号同义表述 | **两件都不该做**：一个被证据链拦住，一个方向本身无效 |

**真正学到的**：`recall@1 83%` 这个数字里，**两处失分都不是缺陷**：

- 「称号」第 3：短 query 的正常水位，top3 内模型能答对
- 「承诺」第 9：跨通道量纲问题，第 191 + 194 轮两次实测证明不可强修

**所以 recall@1 的合理目标就是 83%，不该再去追 100%。**
以后有人（包括我自己）想动这个数字，先看这份文档，别再重复两次失败实验。

## 五、证据保全（防止下次又想去删）

那两条段落**绝对不能删**，因为它们各自是不同 claim 的唯一证据：

```
段落 eed07c28ca9b8747…  →  claim 1e51fabf1ac8b332（superseded）的唯一证据
段落 de34e316df1f473b…  →  claim 9227b4719f6dfcb5（superseded）的唯一证据
```

软删任何一条，`_p179_memory_health.py` 的「无证据的 claim」会从 **0 变成 1**，
这是健康检查的硬指标。

验证工具：`tools/_p195_evidence_check.py`（只读）。
